Cloud IAM: AWS, Azure and GCP side by side

What it is and the problem it solves

In the cloud, everything is an API call: start a VM, read a file from storage, call a model. Identity and Access Management (IAM) decides which identities can make which calls. Identities are people (you, teammates) and, far more often, workloads (your Lambda function, your container, your AI agent). Without IAM done well you get two failures: things break because they lack permission, or, much worse, a small bug lets an attacker use permissions that were far too broad.

The model is the same on every cloud: an identity (who) gets permissions (what actions) on a scope (which resources), and the guiding rule is least privilege: give only what is needed, nothing more. For apps, use a role or managed identity that hands out short-lived credentials automatically, never long-lived keys pasted into code.

Everyday comparison: hotel key cards.
Check-in is authentication (show ID). Your key card is a role: it opens your room, the gym and the lift, nothing else. That is least privilege. The cleaner's card opens many rooms but only during working hours: a condition. The card stops working at checkout: short-lived credentials. Giving a guest the master key because it is easier is how breaches happen.

Benefits of least privilege

  • A bug or stolen credential can only reach a small slice of your system.
  • Clear audit trail of who can do what.
  • Required by most enterprise customers and compliance reviews.

Trade-offs

  • More setup: you must figure out exactly which actions an app needs.
  • "Access denied" errors during development are common and slow you down.
  • Permissions drift over time and need periodic review.

Pattern card: least-privilege workload identity

What it is
Each app component gets its own cloud identity with only the permissions it needs, and receives short-lived credentials automatically.
Metaphor
A hotel key card that opens only your room, until checkout.
Real example
Capital One's 2019 breach: an over-permissioned role on a web firewall server could list and read S3 buckets.
Use when
Always, for anything that runs in the cloud and touches other cloud resources.
Do not use when
There is no real exception; in a throwaway sandbox you may relax scopes, but still avoid long-lived keys.
Trade-offs
Some setup and debugging time in exchange for a far smaller blast radius.
Instruction to give AI or a teammate
Give the API container its own managed identity (or IAM role) with read-only access to the uploads bucket and invoke rights on the one model endpoint, no keys in code, and deploy from CI using OIDC.

Real company: Capital One (2019)

Capital One, running on AWS, had a misconfigured web application firewall (open-source ModSecurity). An attacker tricked it into calling the EC2 instance metadata service, which handed back temporary credentials for the IAM role attached to that server. That role, as Krebs on Security reported, was allowed to list all files in data buckets and read their contents, so the attacker downloaded data from S3. Capital One said the permissions were likely broader than intended. A firewall server needs no access to customer data; a least-privilege role would have made the stolen credentials close to useless.

Why it matters on the job: as an FDE you will be granting an AI agent access to a customer's systems. The customer's security team will ask exactly what that agent's identity can do. IAM is how you answer, and it is the first thing reviewed in every enterprise deployment.

Where it shows up in code you'll read

tap to expand

Good code has no keys in it: the SDK finds credentials from the environment (the role or managed identity). Seeing a key string in code is the red flag.

# Python
s3 = boto3.client("s3")                       # AWS: picks up the IAM role automatically
cred = DefaultAzureCredential()                # Azure: uses the managed identity
# red flag: aws_access_key_id="AKIA..." or an Azure connection string in code
// Java: AWS SDK DefaultCredentialsProvider / Azure DefaultAzureCredentialBuilder - same idea.
// TypeScript: @aws-sdk clients and @azure/identity DefaultAzureCredential.
// The permissions themselves usually live in Terraform / Bicep / CloudFormation files
// (infrastructure as code), not in the app code: look for policy or role assignment blocks.

Interview angle

  • "How would you give an AI agent access to a customer's data on Azure?" Strong answer: a dedicated managed identity per agent, RBAC role assignments scoped to the specific resources, read-only by default, separate identity and approval for write actions, Key Vault for any secrets that can't be avoided, and logging of every access.
  • "Walk me through a cloud breach and how IAM could have stopped it." Strong answer: Capital One: the SSRF got credentials, but over-broad role permissions turned it into a data breach; least privilege, blocking metadata access (IMDSv2 on AWS), and alerting on unusual S3 listing are the fixes.

Glossary

IAM
Identity and Access Management: who can do what on which resources.
Authentication / authorization
Proving who you are / checking what you are allowed to do.
Least privilege
Grant only the permissions actually needed.
IAM role (AWS)
An identity with permissions that apps or people assume temporarily.
Policy
A document listing allowed (or denied) actions on resources.
Entra ID
Microsoft's identity directory, formerly Azure Active Directory.
RBAC
Role-based access control: permissions come from roles assigned to identities at a scope.
Scope
Where a permission applies: whole account, a project/resource group, or one resource.
Managed identity (Azure)
An identity Azure creates for your app so it can get tokens without secrets.
Service account (GCP)
GCP's identity for an app or workload.
STS / temporary credentials
Short-lived keys issued for a role, which expire automatically.
OIDC federation
Letting an outside system (e.g. GitHub Actions) prove its identity to the cloud without a stored secret.
Metadata service / IMDSv2
An internal endpoint where a VM gets its own info and role credentials; IMDSv2 is AWS's hardened version.
SSRF
Server-side request forgery: tricking a server into making a request on the attacker's behalf.
WAF
Web application firewall: filters malicious web traffic.
S3 bucket
A container for files in AWS's object storage.
Blast radius
How much damage one failure or compromise can cause.
Infrastructure as code (Terraform, Bicep, CloudFormation)
Cloud resources and permissions defined in files, reviewed and deployed like code.
Key Vault
Azure's service for storing secrets and keys securely (AWS: Secrets Manager; GCP: Secret Manager).
