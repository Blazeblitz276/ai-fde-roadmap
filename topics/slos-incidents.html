SLOs, error budgets and incident handling

Track: Production & ops. Builds on drop 4 (logs, metrics, golden signals) and drop 6 (CI/CD, canary).
Make it reliable is not a requirement anyone can test. Site reliability engineering (SRE) turns it into numbers: what we measure (SLI), the target (SLO), the promise to customers with penalties (SLA), and how much failure we can afford (error budget). Incident handling is what the team does when the numbers go red.

How it works

  1. Pick SLIs users actually feelMeasure at the edge closest to the user (load balancer, API gateway), not CPU. For an LLM app add AI-specific ones: time to first token, % responses passing guardrails, weekly eval score on the golden set (drop 3), cost per request.
  2. Set the SLO with product and engineering togetherStart slightly below what you achieve today; tighten later. 100% is never the goal: users cannot tell 99.99% from 100% through their own Wi-Fi, and every extra nine multiplies cost.
  3. Alert on burn rate, not single errorsBurn rate = how fast you are spending the budget. Spending a month of budget in an hour pages someone now; a slow burn opens a ticket. This kills noisy 3 a.m. alerts.
  4. Run incidents with rolesDeclare early, assign severity (SEV1 = customers broadly impacted). One incident commander coordinates, one person handles communications (status page, customer), others fix. Mitigate first (roll back, fail over), find root cause later.
  5. Blameless postmortem and the budget policyWrite what happened, timeline, impact, why the system allowed it, and action items with owners. If the budget is exhausted, the agreed policy kicks in, for example freezing non-urgent releases until reliability recovers.
Everyday comparison: your monthly mobile data plan.
A 99.9% SLO is like a plan that allows about 43 minutes of bad service per month. While you have data left you can stream freely (ship features, run experiments). If one binge eats a big chunk in a day (fast burn), you get a warning SMS immediately (page). Run out before month end and you stop streaming (release freeze) until it resets. Nobody buys an infinite plan because it costs too much: that is why nobody targets 100%.

When to use / when not to use

Solid arrows = yes, dashed = no.

Trade-offs: a tighter SLO means more redundancy, slower releases and more on-call load; a looser one means unhappy users. Too many SLOs and nobody watches them; pick a few per user journey. Do not set SLOs on things users never notice (CPU, memory); those belong on debugging dashboards.

Pattern card: error-budget policy

What it is
A written, pre-agreed rule for what happens when the error budget runs out, so reliability vs features is decided by data, not by whoever argues loudest.
Metaphor
The monthly data plan: spend freely while you have budget, stop streaming when it is gone.
Real example
Google's example error budget policy in the SRE Workbook (below).
Use when
A service has real users, more than one team ships to it, and there is tension between speed and stability.
Do not use when
Early prototypes and pilots with a handful of friendly users; measure, but do not freeze anything yet.
Trade-offs
Needs good SLI data and leadership buy-in; in return removes politics from release decisions.
Instruction to AI / a teammate
Define two SLOs for the support assistant (99.5% of requests succeed and 95% return the first token within 2 seconds, over 28 days), build them from our existing OpenTelemetry metrics, add fast and slow burn-rate alerts to on-call, and draft an error budget policy that freezes non-urgent releases when the budget is spent.

Real-world scenario and why it matters on the job

Google SRE (The Site Reliability Workbook, chapter Implementing SLOs and the Example Error Budget Policy appendix): an error budget is 1 minus the SLO, so a service with a 99.9% availability SLO receiving 1,000,000 requests in four weeks may fail 1,000 of them. The example policy says that if the service has exceeded its error budget for the preceding four-week window, the team halts all changes and releases other than P0 issues or security fixes until it is back within SLO. If a single incident consumes more than 20% of the error budget over four weeks, the team must write a postmortem with at least one P0 action item. The workbook stresses that the product manager, developers and SREs must all approve the SLO and the policy, and that the policy is not a punishment.

Why it matters: when you hand an AI system to a customer (drop 6, pilot to production), who gets paged, for what, and what happens after is part of production readiness. Proposing SLOs that include AI quality (eval score) and cost, not only uptime, shows architect-level thinking.

Where it shows up in code you'll read

# Python, conceptually: error budget and burn rate from two counters
slo = 0.999
total = metrics.count('requests', window='28d')
failed = metrics.count('errors', window='28d')
budget = (1 - slo) * total            # e.g. 1,000 allowed failures
remaining = budget - failed

burn_rate_1h = metrics.error_ratio(window='1h') / (1 - slo)
if burn_rate_1h > 14:                 # a 30-day budget gone in about 2 days
    page_on_call('SEV2: chat API burning error budget fast')

FDE / architect interview angle

  • How would you define reliability for an LLM-powered support assistant? Strong answer: user-journey SLIs (success rate, time to first token, end-to-end latency p95), a quality SLI from regular evals and guardrail pass rate, cost per conversation; 2-4 SLOs agreed with the business; burn-rate alerting; an SLA looser than the SLO; and a fallback (simpler model, human handoff) when the model provider is down.
  • Walk me through how you would run a SEV1. Strong answer: declare, name an incident commander and a comms lead, stabilise first (roll back the canary, fail over, switch model), keep a timeline, regular customer updates, then a blameless postmortem with owned action items and a check of the error budget policy.

Glossary

SRE
Site reliability engineering: running production with software engineering methods and numeric reliability targets.
SLI
Service level indicator: a measured ratio users feel, e.g. % of fast, successful requests.
SLO
Service level objective: the internal target for an SLI over a window.
SLA
Service level agreement: a contractual promise with penalties; looser than the SLO.
Error budget
1 - SLO: the amount of failure you are allowed in the window.
Burn rate
How fast the error budget is being used compared with an even spend.
Window
The time period an SLO is measured over, e.g. rolling 28 days.
The nines
Shorthand for availability: three nines = 99.9%.
p95 latency
95% of requests are faster than this value.
Time to first token
How long until an LLM starts streaming its answer.
On-call / paging
The engineer responsible for responding to urgent alerts / the urgent alert itself.
Incident / SEV levels
An unplanned disruption / severity scale (SEV1 most severe).
Incident commander
The person coordinating the response, not necessarily fixing it.
Mitigation
Stopping the user impact (rollback, failover) before finding the root cause.
Root cause
The underlying reason the system allowed the failure.
Blameless postmortem
A written review that focuses on system and process fixes, not on blaming people.
P0
Highest-priority work item: drop everything else.
Release freeze
Pausing non-urgent deployments to protect stability.
Status page
Public page telling customers about ongoing incidents.
