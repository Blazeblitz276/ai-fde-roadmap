Architecture patterns part 2: bulkhead, sidecar, strangler fig, saga

Track: SE and architecture patterns. Drop 3 covered API gateway, circuit breaker and retry; these four answer: how do I contain failure, add shared plumbing, replace an old system safely, and keep data consistent across services?
Four patterns, four everyday pictures: ship compartments (bulkhead), a motorcycle sidecar (sidecar), a vine slowly replacing a tree (strangler fig), and a travel booking you can undo step by step (saga).

What they are and the problems they solve

PatternProblemOne-line idea
BulkheadOne slow dependency eats all threads/connections and the whole service diesGive each dependency or tenant its own capped pool, so a failure stays in its compartment
SidecarEvery service, in every language, re-implements TLS, retries, logging, metricsRun that plumbing as a separate helper process deployed next to each service
Strangler figA big legacy system must be replaced, but a big-bang rewrite is too riskyRoute traffic through a facade and move one slice at a time to the new system until the old one can be deleted
SagaA business action spans several services/databases and there is no single transactionRun a sequence of local steps; if one fails, run compensating steps to undo the earlier ones

How they work

Bulkhead: separate pools per dependency.

Sidecar: the app talks to localhost; the sidecar handles the network.

Strangler fig: a facade routes each slice to old or new.

Saga (orchestrated): each step has an undo.

Everyday comparisons.
Bulkhead: a ship's hull is split into watertight compartments, so one leak floods one compartment, not the ship. Sidecar: a motorcycle sidecar carries luggage so the rider just rides; swap the sidecar without rebuilding the bike. Strangler fig: a fig vine grows around a tree until it stands on its own and the old tree can go; you renovate a house room by room while still living in it. Saga: booking a trip as flight, then hotel, then car; if the car fails, you cancel the hotel and the flight, because there is no single 'book everything or nothing' button.

When to use / when not to use

PatternUse whenDo not use whenMain trade-off
BulkheadA service calls several dependencies of different reliability (LLM, payments, search) or serves many tenantsOne dependency only, or a tiny service; pools add tuning workIsolation vs some idle capacity and pool sizing effort
SidecarMany services in many languages need the same plumbing (mTLS, telemetry, auth); Kubernetes / Container Apps platformsA handful of services in one language (a library is simpler); very latency-sensitive hopsConsistency and language independence vs an extra process per instance (CPU, memory, a small hop)
Strangler figReplacing or splitting a legacy system that must stay online; incremental migration to cloudSmall systems you can rewrite in weeks; when you cannot put a facade in front of the old systemLow risk and steady progress vs running two systems (and sometimes dual writes) for a long time
SagaBusiness transactions across services/databases: orders, bookings, onboarding, multi-step agent actionsEverything lives in one database (use a normal transaction); steps that cannot be undone and need strict atomicityAvailability and independence vs eventual consistency and designing compensations for every step

Pattern cards

Bulkhead: what
Separate, capped pools (threads, connections, concurrency) per dependency or tenant so one failure cannot exhaust shared resources.
Bulkhead: metaphor + example
Ship compartments. Netflix Hystrix gave each dependency its own fixed-size thread pool and rejected calls when it was full; Lyft's Envoy sidecars let a service owner cap concurrent requests per calling service.
Bulkhead: instruction
Wrap the LLM, payments and search clients in separate Resilience4j bulkheads (10, 20, 20 concurrent calls), return a fast fallback when the LLM bulkhead is full, and expose bulkhead rejections as a metric.
Sidecar: what
A helper container deployed with each app instance that handles cross-cutting concerns (proxying, mTLS, logs, config) outside the app code.
Sidecar: metaphor + example
Motorcycle sidecar. Lyft built Envoy and ran it next to every service; by 2016 it handled all edge and service-to-service traffic, a mesh across 100+ services. Istio, Dapr (used by Azure Container Apps) and log/agent collectors use the same idea.
Sidecar: instruction
Enable the Dapr sidecar on our Container Apps for service invocation and pub/sub, turn on mTLS between services, and send traces to Application Insights through OpenTelemetry, with no networking code in the services themselves.
Strangler fig: what
Put a facade in front of the legacy system and move features one at a time to new code, then delete the old parts.
Strangler fig: metaphor + example
Vine around a tree; room-by-room renovation. Shopify used a 7-step strangler fig to pull settings logic out of its huge Shop model: new interface, redirect reads, new table, dual-write, backfill, switch reads, delete old code.
Strangler fig: instruction
Put Azure API Management in front of the legacy claims app, route only /claims/status to the new service behind a feature flag at 5% traffic, compare responses for two weeks, then ramp to 100% and remove the old endpoint.
Saga: what
A long business transaction split into local steps, each with a compensating action, coordinated by an orchestrator or by events (choreography).
Saga: metaphor + example
Trip booking you unwind in reverse. Uber built Cadence, an open-source workflow engine for long-running, fault-tolerant workflows with saga support (compensations run in reverse on failure); Temporal grew out of the same team.
Saga: instruction
Model checkout as an orchestrated saga in Step Functions (or Temporal): reserve stock, charge card, book courier; give every step an idempotent compensation (release, refund), retry transient errors three times, and alert a human if a compensation fails.

Real companies and why it matters

  • Lyft (sidecar + bulkhead): Matt Klein's 'Envoy joins the CNCF' post explains that Lyft developers did not trust moving critical functionality out of the monolith because the network was a black box. Envoy, deployed as a sidecar next to every service, made networking and observability consistent, and Lyft later described using it to cap concurrency per caller to stop cascading failures (InfoQ case study).
  • Netflix (bulkhead): Hystrix (open source, now in maintenance mode; Resilience4j is the usual successor) isolated each dependency in its own thread pool so a slow one could not starve the rest.
  • Shopify (strangler fig): 'Refactoring Legacy Code with the Strangler Fig Pattern' walks through the incremental, reversible extraction from the Shop model.
  • Uber (saga): Cadence powers long-running workflows at Uber; its samples include a saga with compensations.
  • On the job: as an FDE you rarely get a greenfield system. You will be asked to modernise a customer's legacy app (strangler fig), add AI calls without destabilising it (bulkhead), and make multi-step agent actions safe to fail halfway (saga).

Where it shows up in code you'll read

# Python, conceptually
llm_pool = Semaphore(10)                 # bulkhead: max 10 LLM calls in flight
if not llm_pool.acquire(timeout=0.05):
    return fallback_answer()             # reject fast instead of piling up

# saga step with compensation
saga.step(reserve_stock, undo=release_stock)
saga.step(charge_card,   undo=refund)
saga.step(book_courier)                  # failure => refund, then release_stock

Interview angle

  • 'How would you migrate a customer's monolith to the cloud without downtime?' Strong answer: strangler fig behind a gateway, pick a low-risk high-value slice first, feature flags and shadow/compare traffic, data migration via dual-write + backfill, measure, ramp, delete old code; avoid big-bang rewrites.
  • 'How do you keep data consistent when an order spans payment, inventory and shipping services?' Strong answer: saga (orchestrated for visibility, choreographed for loose coupling), idempotent steps and compensations, outbox pattern for reliable events, and accept eventual consistency with clear user-facing states.

Glossary

Thread pool / connection pool
A fixed set of reusable workers or connections a program shares across requests.
Cascading failure
One component's failure overloads others, which then fail too, spreading through the system.
Fallback
A cheaper backup response used when the real call is unavailable.
Proxy
A program that sits in the middle and forwards network traffic, adding features on the way.
Envoy
Open-source proxy created at Lyft, the most common sidecar proxy.
Service mesh
A layer of sidecar proxies plus a control plane that manages all service-to-service traffic (Istio, Linkerd).
Control plane / data plane
Control plane decides and distributes configuration; data plane (the proxies) carries the actual traffic.
mTLS
Mutual TLS: both sides of a connection prove their identity with certificates and the traffic is encrypted.
Dapr
Distributed Application Runtime: an open-source sidecar offering service calls, pub/sub, state and secrets via simple APIs; built into Azure Container Apps.
Facade
A front door that hides what is behind it and routes calls.
Feature flag
A switch in config that turns a code path on or off, or on for a percentage of users.
Dual-write / backfill
Writing to old and new stores at once during migration; copying existing historical data into the new store.
Distributed transaction / 2PC
Trying to commit across several databases atomically; two-phase commit is the classic, but it is slow and fragile across services.
Compensating action
A step that semantically undoes an earlier step (refund for charge).
Orchestration vs choreography
A central coordinator tells each step what to do, vs each service reacts to events from the others.
Eventual consistency
Data across services may disagree briefly but converges to the correct state.
Outbox pattern
Write the business change and the event to publish in the same local transaction, then a relay publishes the event reliably.
Temporal / Cadence / Step Functions / Durable Functions
Workflow engines that persist each step so long processes survive crashes (Temporal, Uber Cadence, AWS, Azure respectively; GCP equivalent: Workflows).
