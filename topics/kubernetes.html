Kubernetes basics: GKE vs EKS vs AKS, and when you do not need it

Track: Cloud + Production & ops. Builds on drop 4 (serverless containers) and drop 1 (stateless services).
Kubernetes (K8s) is an open-source system that runs containers across a fleet of machines and keeps them in the state you describe: 'I want 5 copies of this API, each with 1 CPU, reachable at this address'. GKE, EKS and AKS are Google's, Amazon's and Microsoft's managed versions.

What it is and the problem it solves

Once you have dozens of containers, someone must decide which machine each runs on, restart crashed ones, add copies under load, roll out new versions without downtime, route traffic between them and hand them secrets. Doing that by hand does not scale. Kubernetes automates it with a 'desired state' model: you write what you want (YAML), and controllers keep fixing reality until it matches.

How it works

  1. 1. DescribeYou (or the AI) write YAML: a Deployment with the image, replica count, CPU/memory, health checks; a Service; an Ingress.
  2. 2. ScheduleThe scheduler places pods on nodes with free capacity (and GPUs if requested).
  3. 3. ReconcileControllers constantly compare desired vs actual: a crashed pod is replaced, a dead node's pods move elsewhere.
  4. 4. Scale and roll outHPA adds pods under load; a node autoscaler adds VMs when pods do not fit; new versions roll out pod by pod and can be rolled back.
Everyday comparison: an airport operations centre.
The control tower (control plane) does not fly planes; it holds the schedule (desired state), assigns each flight to a gate (scheduling), reroutes when a gate breaks (self-healing) and opens more gates at rush hour (autoscaling). Planes are pods, gates are nodes. Managed Kubernetes = the airport authority runs the tower for you; you still own the flights.

When to use / when not to use

Benefits

  • Self-healing, rolling updates and autoscaling for many services in one place.
  • Portable: the same YAML runs on GKE, EKS, AKS or on-prem; huge ecosystem (Helm, Argo CD, KEDA, Istio).
  • Fine control over GPUs, scheduling, networking and sidecars; good for AI training and inference fleets.

Trade-offs

  • Steep learning curve and real operational work (upgrades, security, networking) even when 'managed'.
  • Easy to over-provision: idle nodes cost money; needs FinOps (drop 3).
  • Overkill for an MVP; a serverless container platform ships faster.

Pattern card: start serverless, graduate to Kubernetes

What it is
Package everything as containers from day one, run them on a serverless container platform, move to managed Kubernetes only when a concrete need appears.
Metaphor
Rent a furnished flat before buying and running a building.
Real example
OpenAI (2021) scaled single Kubernetes clusters to 7,500 nodes on Azure VMs for training GPT-3, CLIP and DALL-E, a case where K8s pays off; most MVPs never reach that need.
Use when
New customer projects, uncertain scale, small teams.
Do not use when
The customer already runs a mature Kubernetes platform; deploy onto it instead of adding another runtime.
Trade-offs
Some serverless limits (request timeouts, GPU options, sidecars) may force the move later; containers keep that move cheap.
Instruction to AI / a teammate
Containerise the API and worker with health checks and no local state, deploy them to Azure Container Apps now, keep the manifests simple enough to port to AKS, and write down the three triggers (GPU scheduling, more than 15 services, mesh requirements) that would make us move.

Real-world scenario and why it matters on the job

OpenAI's January 2021 post 'Scaling Kubernetes to 7,500 nodes' explains why they chose Kubernetes for ML research: one simple infrastructure that lets researchers scale up without changing code. It also shows the cost: they had to move off the Flannel network plugin to Azure-native pod networking for throughput, run API servers and etcd on dedicated nodes, and add gang scheduling for large MPI training jobs. Lesson for an architect: Kubernetes is powerful at scale and for GPUs, and it needs real platform engineering.

On the job: enterprise customers (banks, insurers, telcos) very often already run AKS or EKS, and their platform team will expect your AI service as a container with Helm charts, health probes and resource limits. CV tie-in: GPU inference for vision models is a classic Kubernetes workload (GPU node pools, autoscaling on queue length with KEDA).

// What you will see in repos: Dockerfile, k8s/ or charts/ folders (Helm), values.yaml per environment,
//   kustomization.yaml, or Argo CD 'Application' files (GitOps).

FDE / architect interview angle

  • 'Would you put this customer's new AI app on Kubernetes?' Strong answer: depends on team, scale and constraints; start serverless containers unless there is a platform team, GPU scheduling needs, many services or an existing cluster; containerise anyway so the move is cheap.
  • 'How do pods get cloud permissions without keys?' Strong answer: workload identity (GKE Workload Identity, EKS Pod Identity/IRSA, Entra Workload ID) maps a Kubernetes service account to a cloud identity with least privilege (drop 1 IAM).

Glossary

Container
A packaged app with everything it needs to run, identical on a laptop and in the cloud.
Orchestration
Automatically placing, starting, healing and scaling many containers.
Control plane
The managing brain of a cluster (API server, scheduler, controllers, etcd).
etcd
The small database where Kubernetes stores the desired and current state.
Desired state / reconcile
What you declared / the loop that keeps changing reality to match it.
Cluster, node, pod, deployment, service, ingress, HPA, namespace
See the table at the top of this topic.
YAML
A plain-text format of key: value lines used for configuration.
kubectl
The command-line tool to talk to a Kubernetes cluster.
Helm / chart
A packaging tool for Kubernetes apps / one package of templates.
GitOps / Argo CD
Keeping cluster config in git and letting a tool apply it automatically.
Readiness probe
A health check that tells Kubernetes when a pod can receive traffic.
Autopilot / Auto Mode / AKS Automatic
Hands-off cluster modes where the provider also manages nodes.
Workload identity
Giving a pod a cloud identity without storing keys.
KEDA
Event-driven autoscaler that scales pods on queue length or other events.
CNI / Flannel
The plugin that gives pods network addresses / one such plugin.
Gang scheduling / MPI
Starting all pods of a job together / a standard for many machines cooperating on one training job.
