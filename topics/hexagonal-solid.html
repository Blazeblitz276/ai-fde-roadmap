What it is and the problem it solves

Hexagonal architecture (Alistair Cockburn's "ports and adapters") and clean architecture (Robert C. Martin's version, also called onion architecture in a close variant) share one idea: keep the business rules in the centre, and make databases, web frameworks, LLM providers and other outside systems plug into that centre through interfaces. Dependencies point inward: the core never imports the database library; the database code imports the core's interface.

The problem it solves: in a "big ball of mud", business logic is mixed with SQL, HTTP and SDK calls. Changing the database, the API style or the LLM vendor then means rewriting business logic and retesting everything. With ports and adapters, you swap the adapter and the core stays untouched, and you can unit-test the core with fake adapters in milliseconds.

SOLID is five class-level design principles that make this possible inside the code:

LetterPrinciplePlain meaningSmell when broken
SSingle responsibilityA class has one reason to changeA 2,000-line OrderService that also sends emails and formats PDFs
OOpen/closedAdd behaviour by adding code, not editing working codeA growing if/else on provider name every time a vendor is added
LLiskov substitutionAny implementation of an interface can stand in without surprisesA subclass that throws 'not supported' for half the methods
IInterface segregationSmall focused interfaces, not one giant oneCallers forced to implement 20 methods they never use
DDependency inversionDepend on interfaces (ports), not concrete classes; inject the concrete oneBusiness code calling new PostgresClient() directly

How it works

  1. Request arrives at a driving adapterThe HTTP controller turns JSON into a plain command object and calls the use case. It contains no business rules.
  2. Use case runs the business rulesSubmitClaim validates, applies policy, and asks its output ports for what it needs: 'save this claim', 'summarise this document'.
  3. Driven adapters do the I/OPostgresClaimRepository and AzureOpenAiLlmClient implement those ports. Swapping to DynamoDB or Bedrock = a new adapter plus a config change.
  4. Wiring at startupA composition root (Spring's dependency injection, or a small factory in TypeScript) decides which adapter is plugged into which port.
Everyday comparison: a laptop and its ports
Your laptop's motherboard (the core) does not care whether you plug in a Dell or an LG monitor; it only knows the USB-C port standard. Each device brings its own adapter cable. Change the monitor, keep the laptop. Clean architecture is building your business logic like the motherboard.

When to use / when not to use

Solid arrows = yes, dashed = no.

BenefitCost / risk
Swap databases, LLM vendors, APIs with little blast radiusMore files, interfaces and indirection; harder for newcomers to follow a request
Fast unit tests of business rules with fake adaptersMapping between domain objects and database/API objects is boilerplate
Same core exposed as REST, queue consumer, and an MCP tool for agentsOver-engineering when the 'business logic' is just saving a form
Clear rule for AI agents: where each kind of code belongsPurists argue about layers; agree a simple convention and stop

Real-world scenario (verified)

Netflix Studio engineering
Netflix's 'Ready for changes with Hexagonal Architecture' (Netflix Tech Blog, Mar 2020) describes a studio app whose data was spread across many services (gRPC, JSON API, GraphQL) while a monolith was being broken up. They kept entities, repositories (ports) and interactors (use cases) independent of data sources. When a new GraphQL microservice came online, they 'managed to transfer reads from a JSON API to a GraphQL data source within 2 hours', because persistence details never leaked into business logic.
Why it matters on the job
FDE work is integration-heavy: every customer has a different CRM, document store, identity provider and preferred LLM cloud. A ports-and-adapters core lets one product be deployed for an Azure customer and an AWS customer with different adapters, and lets you add an agent tool interface without touching the rules.

Pattern card: hexagonal (ports and adapters)

What it is
Business core in the middle, talking to the outside only through interfaces (ports) that swappable adapters implement.
Metaphor
Laptop motherboard with standard ports; devices bring their own adapters.
Real example
Netflix Studio app swapping a JSON API data source for a GraphQL microservice in 2 hours.
Use when
Long-lived services with real rules and several integrations or likely vendor changes.
Do not use when
Prototypes, scripts, or thin CRUD where there is almost no logic to protect.
Trade-offs
Changeability and testability vs more files, mapping code and indirection.
Instruction to AI / a teammate
Structure this service as ports and adapters: business rules in core/ with no framework or SDK imports, one interface per external system (DB, LLM, email), adapters in adapters/, wired in one composition root, and unit-test the core with fakes.

Pattern card: SOLID (as a review checklist)

What it is
Five principles for classes and modules that keep code easy to extend and test.
Metaphor
A well-run kitchen: each station has one job (S), new dishes add stations rather than rebuilding old ones (O), any trained chef can cover a station (L), each station has only the tools it needs (I), and chefs ask for 'a knife', not 'Ravi's knife' (D).
Real example
Spring's dependency injection and Java interfaces are built around D and I; the Netflix example above relies on D.
Use when
Reviewing AI-generated code and designing services with several implementations.
Do not use when
As dogma: a single implementation rarely needs an interface 'just in case'.
Trade-offs
Flexible, testable code vs more abstractions to navigate.
Instruction to AI / a teammate
Refactor so each class has one reason to change, external systems sit behind small interfaces injected via the constructor, and adding a new LLM provider means adding a class, not editing existing ones.

FDE / architect interview angle

  • The customer wants your product on Azure OpenAI today but may move to Bedrock next year. How do you design for that? Strong answer: an LlmClient port with Azure and Bedrock adapters, configuration-driven wiring, provider-neutral prompts and eval suite run against both, and keep provider-specific features behind the adapter.
  • Walk me through how you'd review a large AI-generated pull request. Strong answer: check layering first (rules out of controllers, no SDK calls in the core), SOLID smells (god classes, provider if/else chains), test coverage of the core, then naming and details.

Glossary

Hexagonal architecture / ports and adapters
Business core surrounded by interfaces (ports) that interchangeable adapters implement.
Clean / onion architecture
Close relatives: concentric layers where dependencies only point inward to the domain.
Port
An interface the core defines: either an entry (use case) or a need (repository, LLM client).
Adapter
Code that connects a port to a real technology (Postgres, Azure OpenAI, HTTP).
Driving vs driven adapter
Driving adapters call into the core (controllers); driven adapters are called by the core (databases, APIs).
Domain / entity
The business concepts and their rules (Claim, Policy).
Use case / interactor
One business action, such as SubmitClaim.
Repository
An interface for saving and loading domain objects, hiding the database.
Dependency injection
Passing a class the objects it needs instead of letting it create them.
Composition root
The one place at startup where concrete adapters are wired to ports.
Monolith / microservice
One big deployable app / small independently deployed services.
God class
A class that does far too much; the opposite of single responsibility.
Big ball of mud
Code with no clear structure where everything depends on everything.
