Agent memory and multi-agent orchestration patterns

Track: Agentic systems. Builds on drop 1 (how agents call tools) and drop 2 (MCP).
An LLM forgets everything between calls: each request starts blank. 'Memory' is everything the system around the model does to put the right past information back into the prompt. 'Multi-agent orchestration' is how you split a big job across several LLM workers, each with its own instructions, tools and context window, and who coordinates them.

How it works

  1. Write memoryAfter a turn, the system (or the model, via a 'remember' tool) extracts durable facts or a summary and stores them with metadata: who, when, source. Good systems also let the user see and delete memories.
  2. Read memoryBefore the next call, retrieve only what is relevant (by user id, by similarity search like RAG, by recency) and put it into the prompt. Memory is basically RAG over your own history.
  3. Manage the context windowWhen a conversation gets long, summarise older turns (compaction), or save the plan to an external store so it survives truncation.
  4. OrchestrateThe lead agent breaks the task down and gives each worker a clear brief: goal, tools, output format, limits. Workers run with fresh, focused context windows, often in parallel, and return condensed results, not their whole history.
  5. Synthesise and stopThe lead merges results, decides if more work is needed, and stops at a budget limit (max agents, max steps, max tokens).
Everyday comparison: a restaurant kitchen with a notebook.
The head chef (orchestrator) reads the order, splits it into tasks for the grill, salad and dessert stations (workers). Each station focuses only on its dish and sends back the plate, not a story of how they cooked it. The head chef plates everything together (synthesis). The order book and the 'regular customer: no onions' card on the wall are memory: without them, every visit starts from zero.

Memory trade-offs: more memory means more personalisation but also more privacy risk, stale or wrong facts that keep resurfacing, and a new attack surface (a poisoned memory is a prompt injection that lasts forever; see topic 3). Always let users view and delete memories.

Pattern cards

Orchestrator-worker: what it is
A lead agent plans and delegates sub-tasks to parallel worker agents with their own context windows, then merges results.
Metaphor
Head chef and stations; a project lead and their team.
Real example
Anthropic's Research feature in Claude (details below).
Use when
Breadth-first tasks with independent parts that exceed one context window, and the value justifies the token cost.
Do not use when
Parts depend tightly on each other, all agents need the same shared context, or the task is simple.
Trade-offs
Faster and more thorough on broad tasks; many times the cost; harder evals (judge the path, not just the answer).
Instruction to AI / a teammate
Build a lead agent that splits a market-research question into at most 5 parallel worker agents, each with web search only and a 20k-token budget, returning a 300-word summary with sources; the lead merges them, and log every worker's trace so we can evaluate it.
Long-term memory: what it is
Store durable facts and summaries outside the model and retrieve the relevant ones into each new prompt.
Metaphor
A doctor's patient file: read before each visit, updated after.
Real example
ChatGPT memory: 'saved memories' plus 'reference chat history' (expanded April 2025), viewable and deletable in Settings.
Use when
Returning users, personal assistants, long-running projects, agents that should learn from past failures.
Do not use when
Anonymous one-shot queries, or regulated data you are not allowed to retain.
Trade-offs
Personalisation vs privacy, staleness, and memory poisoning.
Instruction to AI / a teammate
Add a per-user memory store: after each session extract at most 5 durable facts with source and date, retrieve the top 5 relevant ones into the system prompt, expire facts after 180 days, and give users a page to view and delete them.

Real-world scenario and why it matters on the job

Anthropic, 'How we built our multi-agent research system' (June 2025): Claude's Research feature uses an orchestrator-worker design. A lead agent analyses the query, saves its plan to memory (because context beyond 200,000 tokens gets truncated), spawns subagents that search in parallel, then a citation agent attributes sources. On Anthropic's internal research eval, a Claude Opus 4 lead with Claude Sonnet 4 subagents beat single-agent Opus 4 by 90.2%. The catch they state openly: multi-agent runs use about 15 times the tokens of a chat, and token usage alone explained 80% of the performance difference on their browsing eval. So it is worth it only for high-value, broad tasks, and they note it suits poorly domains where all agents need the same context.

OpenAI's ChatGPT shows the memory side: specific 'saved memories' plus, since April 2025, the option to draw on past chat history, both switchable off under Settings, Personalization, Memory.

Why it matters: customers will ask for 'a multi-agent system' because it sounds advanced. A strong architect asks whether one agent with tools would do, and puts a budget cap on any orchestrator. Cloud names to know (they rename often, check the console): Azure AI Foundry Agent Service (connected agents, multi-agent workflows; Microsoft Agent Framework), AWS Bedrock AgentCore (including AgentCore Memory), Google Vertex AI Agent Engine with the Agent Development Kit (ADK) and Memory Bank.

FDE / architect interview angle

  • 'When would you use multiple agents instead of one?' Strong answer: only when work splits into independent parallel parts, exceeds one context window, or needs clearly separate specialists; cite the cost (Anthropic's ~15x tokens), add budget caps, trace every agent, and evaluate trajectories.
  • 'How would you give an assistant memory across sessions?' Strong answer: separate session state from long-term facts, extract facts with source and timestamp, retrieve by relevance, expire stale ones, let users view and delete, and treat memory writes as a security surface (no writing memories straight from untrusted documents).

Glossary

Agent
An LLM running in a loop that can call tools and decide its next step (drop 1).
Context window
The maximum text (in tokens) a model can read in one request.
Token
A small piece of text that models read and are billed by.
Compaction / summarisation
Replacing old conversation turns with a shorter summary to save context space.
Semantic / episodic / procedural memory
Facts / past events / how-to knowledge.
Vector store
A database that finds items by meaning similarity, used for retrieval (RAG).
Orchestrator (lead, supervisor)
The agent that plans and delegates to others.
Worker / subagent
An agent given one sub-task by the orchestrator.
Handoff
Passing the conversation from one agent to another specialist agent.
Trajectory / trace
The full record of steps and tool calls an agent took.
Budget cap
A hard limit on steps, agents, tokens or money for a run.
Memory poisoning
Planting false or malicious content in an agent's memory so it affects future sessions.
ADK
Google's Agent Development Kit for building agents.
AgentCore
AWS Bedrock's managed services for running agents (runtime, memory, identity, tools).
