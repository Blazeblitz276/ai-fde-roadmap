Serverless containers: Cloud Run vs Azure Container Apps vs AWS

Track: Cloud. This is the middle ground you will use most for AI-built apps: bring a container, the cloud runs and scales it.
Important 2026 update: AWS App Runner stopped accepting new customers on 30 April 2026 (existing customers keep it, no new features). For new apps AWS points to Amazon ECS Express Mode, which sets up ECS on Fargate with a load balancer and auto scaling from one container image.

What it is and the problem it solves

You have a Next.js frontend and a Python FastAPI backend, both packaged as Docker containers. Options: rent VMs (EC2) and manage OS patches, scaling and load balancers yourself; run Kubernetes (powerful, but a platform to operate); use functions (Lambda) but they have time limits and need code shaped as handlers. Serverless containers sit in the middle: give the cloud a container image, it gives you an HTTPS URL, scales instances with traffic (often down to zero), and bills for what runs.

How it works

  1. 1. PackageThe app becomes a container image that listens on a port. Your code must be stateless (drop 1): no files or sessions kept on the instance, because instances come and go.
  2. 2. Deploy a revisionEach deploy creates an immutable revision. You can split traffic (e.g. 10% to the new revision) and roll back instantly.
  3. 3. ScaleThe platform adds instances when requests or queue messages pile up and removes them when idle. Scale to zero saves money but the first request after idle has a cold start (seconds); set min instances to 1 for user-facing APIs that must be snappy.
  4. 4. Connect securelyGive the service an identity (drop 1 IAM: service account / managed identity / task role) to read secrets, the database and the LLM endpoint without keys in code; use private networking (VPC) for databases.
Everyday comparison: ways to run a food business.
VMs are owning a restaurant: you fix the plumbing. Kubernetes is running a food court: very flexible, but you manage the whole building. Functions (Lambda) are a catering order: great for one dish at a time, with strict time limits. Serverless containers are a cloud kitchen: you bring your recipe and staff packed in a box (container), the kitchen provides stoves, opens more counters when orders spike, and closes them at night so you pay nothing.

When to use / when not to use

Benefits

  • No servers or cluster to patch; HTTPS, scaling and rollbacks built in.
  • Scale to zero (Cloud Run, Container Apps) is ideal for internal tools, demos and spiky AI workloads.
  • Same container runs locally and in the cloud; easy to move between clouds.

Trade-offs

  • Cold starts after idle; big AI images and model loading make them worse.
  • Less control than Kubernetes (networking, sidecars, scheduling).
  • Always-on heavy traffic can be cheaper on reserved VMs or Kubernetes.
  • Stateless only: state must live in a database, cache or storage.

Pattern card: Container-first serverless hosting

What it is
Ship each app as a stateless container to a managed service that handles HTTPS, scaling, revisions and identity.
Metaphor
A cloud kitchen: bring the recipe box, the kitchen scales counters with orders.
Real example
DZ BANK's Cloud Run-first approach (below).
Use when
Web apps, APIs, AI backends calling managed LLMs, queue workers, MVPs going to production.
Do not use when
You need full platform control or a service mesh across dozens of services (Kubernetes), or work is tiny event handlers (functions).
Trade-offs
Speed and low ops vs cold starts and less control.
Instruction to give AI or a teammate
Containerise the Next.js app and the FastAPI service, push to ACR from GitHub Actions, deploy both to one Azure Container Apps environment with a managed identity for Key Vault and Azure OpenAI, min 1 replica for the API and 0 for the worker scaled by Service Bus queue length, and use revision traffic splitting for releases.

Real company: DZ BANK on Cloud Run

In a Google Cloud blog post (March 2024), DZ BANK, which describes itself as Germany's second-largest bank by assets, explains moving from on-prem VMs (55,000+ CPUs) by containerising apps and putting them on Cloud Run or GKE. Cloud Run suits apps with traffic spikes and internal tools idle outside office hours, which now scale to zero instead of running 24/7 on their own VMs; heavy nightly risk calculations that needed hardware control went to GKE. They report 70% less toil and 90% lower infrastructure cost, and new apps are 'Cloud Run-first'.

Why it matters on the job: 'Where do we host this?' is a day-one FDE question. A strong default is serverless containers for the app and API, Kubernetes only when there is a clear reason, and you must know the 2026 AWS change (App Runner closed to new customers, ECS Express Mode recommended) so you do not recommend a dead-end service.

Interview angle

  • 'Host an AI-built Next.js + Python app for a customer on Azure. Walk me through it.' Strong answer: containers in ACR, Container Apps environment (API min 1, worker scale-to-zero on queue), managed identity to Key Vault / Azure OpenAI / database, private networking for data, Application Insights, CI/CD with revision traffic splitting, budgets and alerts.
  • 'Cloud Run vs Kubernetes: when do you pick which?' Strong answer: serverless containers by default for stateless apps (less ops, scale to zero); Kubernetes when you need many services with a mesh, custom scheduling, GPUs at steady load, or the customer already runs a platform team.

Glossary

Container / image
A packaged app with everything it needs to run; the image is the template, the container is a running copy.
Container registry
Storage for images: Artifact Registry (GCP), ACR (Azure), ECR (AWS).
Serverless
You do not manage servers; the provider scales and bills by usage.
Scale to zero
No instances run when there is no traffic, so you pay nothing for idle time.
Cold start
Delay when a new instance starts (pulling the image, booting, loading models).
Revision / traffic splitting
An immutable version of a deployed service; sending a percentage of traffic to each revision.
Fargate
AWS's serverless engine that runs ECS or EKS containers without managing EC2 instances.
ECS / ECS Express Mode
AWS's container orchestrator; Express Mode creates a full app stack (Fargate service, load balancer, auto scaling) from one image.
App Runner
AWS's earlier simple container service; closed to new customers since 30 April 2026.
KEDA
Kubernetes Event-Driven Autoscaling: scales on queue length and other event metrics; used inside Container Apps.
Knative
Open-source serverless layer for Kubernetes; Cloud Run's API is compatible with it.
Application Load Balancer (ALB)
AWS's HTTP load balancer that spreads requests across containers.
Managed identity / service account / task role
The identity a running service uses to access other cloud resources without stored keys (drop 1 IAM).
VPC / private networking
A private network in the cloud so databases are not exposed to the internet.
Toil
Repetitive manual operational work (Google SRE term).
Stateless
The service keeps no data between requests on the instance itself (drop 1).
