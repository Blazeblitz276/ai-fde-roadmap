Embeddings and vector databases

Track: AI/LLM systems. This goes under the hood and into choosing the store. Builds on drops 3, 4 and 5 (RAG evals, improving RAG, beyond RAG).
RAG retrieves by meaning, not by exact words. Embeddings are how meaning becomes numbers, and the vector database is how you search billions of those numbers in milliseconds while respecting who is allowed to see what.

What it is and the problem it solves

PieceOne-line ideaProblem it solves
EmbeddingA list of numbers (a vector, often 256 to 3,072 of them) produced by a model so that similar meanings land close togetherKeyword search misses 'team meeting notes' vs 'group standup summary'
SimilarityDistance between two vectors, usually cosine similarity or dot productTurns 'is this relevant?' into maths
Approximate nearest neighbour (ANN) indexA data structure (HNSW graph, IVF clusters, DiskANN) that finds the closest vectors without comparing against all of themComparing a query with 10 billion vectors one by one is far too slow
Vector database / vector indexStores vectors plus metadata (tenant, permissions, date) and answers 'top k most similar, filtered by X'Search plus filtering plus updates at scale, with backups and access control

Your computer vision background helps here: an image embedding from a CNN or a vision transformer (the layer before the classifier) is exactly the same idea, which is how reverse image search and face matching work. Text and image embeddings can even share one space (CLIP-style models), so you can search photos with words.

How it works: write path and query path

  1. Embed with one model, consistentlyDocuments and queries must use the same embedding model and version. Changing the model means re-embedding everything, so record the model name next to every vector.
  2. Index for speedHNSW builds a navigable graph of neighbours (fast, memory-hungry); IVF groups vectors into clusters and only searches nearby clusters; DiskANN-style indexes keep most data on disk to cut cost. All are approximate: you trade a little recall for a lot of speed.
  3. Filter by metadata, especially permissionsEvery query carries filters such as tenant id and the groups the user belongs to, so search never returns a document the user cannot open.
  4. Combine with keywordsHybrid search (vector + keyword BM25, merged with reciprocal rank fusion) then a reranker usually beats pure vectors, as covered in drop 4.
  5. Keep it freshEdits must re-embed changed chunks quickly; deletes must remove vectors (a compliance issue, not just quality).
Everyday comparison: a supermarket layout.
An embedding is the shelf location of every product: things that are used together sit near each other (pasta near sauces), even if their names share no words. The ANN index is the aisle signage that gets you to the right section without walking every aisle. Metadata filters are the staff-only doors: some shelves you simply are not allowed to browse.

When to use / when not to use

Solid arrows = yes, dashed = no.

Trade-offs: bigger embedding dimensions can improve quality but cost more storage and latency; approximate indexes trade recall for speed; one shared index is simpler but per-tenant namespaces make permission and deletion far safer. Do not reach for a vector database when users search by exact ids, codes or dates.

Pattern card: metadata-filtered semantic retrieval

What it is
Store each chunk's vector with tenant, permission and freshness metadata, and always query top-k nearest neighbours with those filters applied, then rerank.
Metaphor
The supermarket where you are guided to the right aisle but staff-only shelves stay locked.
Real example
Notion AI Q&A queries its vector database with permission filters so users only see content they can access (Notion talk on the turbopuffer blog).
Use when
Enterprise RAG, semantic product search, similar-image search, deduplication.
Do not use when
Exact lookups, structured reporting, or tiny corpora that fit into the model's context (drop 5: long context, CAG).
Trade-offs
Great recall by meaning; costs re-embedding on model change and needs careful permission sync.
Instruction to AI / a teammate
Use pgvector in our existing PostgreSQL for now: one namespace per customer, store embedding model name and ACL groups with each chunk, always filter by the caller's groups, run hybrid search with reranking, and add a job that re-embeds edited pages within five minutes.

Real-world scenario and why it matters on the job

Notion (engineering blog, Two years of vector search at Notion: 10x scale, 1/10th cost): Notion AI Q&A launched in November 2023 and answers questions from a workspace plus connected tools like Slack and Google Drive. In 2024 Notion first moved to a serverless vector setup that separated storage from compute (about 50 percent cost reduction from peak), then migrated its multi-billion-object workload to turbopuffer, a search engine built on object storage. While switching they re-indexed everything, upgraded to a newer embedding model and cut over one generation at a time. Results they report: 60 percent lower search-engine spend, 35 percent lower AWS EMR compute cost, and median (p50) query latency from 70-100 ms down to 50-70 ms.

In a public talk hosted on turbopuffer's blog, Notion engineers describe the query path: embed the question, run vector search with metadata filters that capture permissions, query several sources, rerank, then generate the answer. They describe the system as very write-heavy because users edit pages constantly.

Why it matters: customers rarely fail on the 'similarity maths'; they fail on cost at scale, re-embedding when models change, freshness and permission leaks. An FDE who asks about those four in week one avoids the classic RAG pilot that cannot go to production.

FDE / architect interview angle

  • Design search over 50 million internal documents with per-user permissions. Strong answer: chunk and embed with a recorded model version; store ACL metadata with each chunk and filter at query time; hybrid search plus reranking; incremental re-embedding on edits and hard deletes; choose pgvector vs a managed search service by scale and existing cloud; evaluate with a golden set (drop 3).
  • We want to switch embedding models. What happens? Strong answer: the new vectors live in a different space, so you must re-embed the whole corpus into a new index, run both side by side, compare retrieval metrics on the golden set, then cut over gradually, exactly like Notion's generation-by-generation migration.

Glossary

Embedding
A vector of numbers representing meaning, produced by a model.
Vector / dimension
An ordered list of numbers / how many numbers it has.
Cosine similarity / dot product
Ways to measure how close two vectors are.
Nearest neighbour / top k
The k stored vectors closest to the query.
ANN
Approximate nearest neighbour: fast search that may miss a few true neighbours.
HNSW
Hierarchical Navigable Small World: a graph-based ANN index.
IVF
Inverted file index: clusters vectors and searches only nearby clusters.
DiskANN / ScaNN
Microsoft's disk-friendly ANN algorithm / Google's ANN library.
Recall
Share of truly relevant items that the search actually returned.
Chunk
A piece of a document stored and embedded separately.
Metadata filter
Condition on stored fields (tenant, ACL, date) applied during search.
ACL
Access control list: who may see an item.
Namespace / tenant
A separated slice of the index / one customer or workspace.
Hybrid search / BM25 / RRF
Vector + keyword search / the classic keyword ranking formula / reciprocal rank fusion, a way to merge two ranked lists.
Reranker
A model that re-scores retrieved results more precisely.
pgvector
PostgreSQL extension adding a vector column type and similarity search.
Object storage
Cheap file-like storage such as S3, Blob Storage, Cloud Storage.
p50 latency
Median response time: half of requests are faster.
CLIP-style model
A model that embeds images and text into the same space.
AWS EMR
Amazon's managed big-data processing service (Spark, Hadoop).
