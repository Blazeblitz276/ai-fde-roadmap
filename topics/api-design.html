API design: REST vs GraphQL vs gRPC, versioning, idempotency keys

Track: SE and architecture patterns. Builds on drop 3 (API gateway, retry with backoff) and drop 7 (auth, reading route handlers).
An API is a promise to other teams, customers and now AI agents. A good one is easy to call correctly, hard to call dangerously, and can change without breaking everyone who depends on it.

Three problems every API must solve beyond the style: how to change it safely (versioning), how clients retry without causing damage (idempotency), and how to protect it (auth from drop 7, rate limits from drop 3).

How it works: safe retries with an idempotency key

Dashed = first time (new key), solid = repeat (key already seen).

  1. Why retries are dangerousA request can fail before the server got it, halfway through, or after it succeeded but the reply was lost. The client cannot tell which, so a naive retry of 'charge 100 rupees' may charge twice.
  2. Idempotent by nature vs by keyGET, PUT (set to this value) and DELETE are naturally idempotent: doing them twice ends in the same state. POST (create something) is not, so it needs an idempotency key.
  3. The key mechanismThe client generates a random key per operation and reuses it on every retry. The server stores the key with the result; a repeat returns the stored result, and a repeat with different parameters is rejected.
  4. Combine with backoff and jitterRetries wait exponentially longer with randomness so a struggling server is not hammered (drop 3).
  5. VersioningAdditive changes (new optional fields) are safe; removing or renaming fields is breaking. Options: version in the URL (/v2/), in a header, or Stripe-style dated versions pinned per customer. GraphQL usually evolves by adding fields and deprecating old ones instead of versions; gRPC/protobuf by never reusing field numbers.
Everyday comparison: a restaurant order ticket number.
You order and the waiter writes ticket 57. If you are unsure the kitchen heard, you ask again quoting ticket 57, and the kitchen says 'already cooking 57' instead of making a second biryani. REST is ordering from a fixed menu, GraphQL is telling the waiter exactly which items and sides you want on one plate, and gRPC is the kitchen's internal shorthand between stations: fast and precise, but customers do not speak it. Versioning is printing a new menu while honouring the old one for regulars.

Trade-offs: GraphQL moves complexity to the server (query cost limits, per-field authorization, N+1 database calls); gRPC is opaque to curl and browsers; REST can need many round trips. Do not use GraphQL just to look modern for a simple CRUD backend; do not expose gRPC as a public partner API unless partners asked for it. Idempotency keys cost a storage lookup per write; skip them only for operations that are harmless to repeat.

Pattern card: idempotency key on every create or payment

What it is
Clients send a unique key with each state-changing request; the server performs the work at most once per key and returns the saved result to retries.
Metaphor
The restaurant ticket number that stops a second biryani.
Real example
Stripe's API accepts an Idempotency-Key header on POST requests and returns the saved response for retries with the same key (Stripe API reference and engineering blog).
Use when
Payments, orders, bookings, sending messages, agent tool calls that change things, any job that may be retried by a queue (drop 3).
Do not use when
Pure reads (GET), or naturally idempotent updates like set status = closed.
Trade-offs
A small key store and expiry policy (Stripe prunes after at least 24 hours) in exchange for safe automatic retries.
Instruction to AI / a teammate
Make POST /orders and every agent tool that changes data accept an Idempotency-Key header, store key plus request hash plus response for 24 hours, return the stored response on repeats, reject a reused key with different parameters, and document it in the OpenAPI spec.

Real-world scenario and why it matters on the job

Stripe (API reference, Idempotent requests, and the engineering blog post Designing robust and predictable APIs with idempotency): when charging a customer, a lost response could lead a client to retry and double-charge. Stripe's API lets clients send an Idempotency-Key header (it suggests random V4 UUIDs, up to 255 characters, no personal data in the key). For API v1, Stripe saves the status code and body of the first request once execution begins and returns that saved response to retries with the same key, including errors; it compares parameters and errors if a reused key comes with different ones; keys can be pruned after at least 24 hours. Stripe's client libraries retry automatically with idempotency keys, exponential backoff and jitter.

Why it matters now: AI agents retry. A tool call that times out may be re-issued by the agent framework, the queue, or the model itself. If 'create refund' or 'send email' tools are not idempotent, an agent pilot will eventually double-refund someone. Asking 'what happens if this call is made twice?' in a design review is one of the cheapest ways to sound like an architect.

# Python (FastAPI-style), conceptually
@app.post('/refunds')
def create_refund(body: RefundIn, key: str = header('Idempotency-Key')):
    saved = idem_store.get(key)
    if saved:
        if saved.request_hash != hash(body): raise Conflict()
        return saved.response                 # retry: same answer, no second refund
    result = payments.refund(body.order_id, body.amount)
    idem_store.put(key, hash(body), result, ttl_hours=24)
    return result

FDE / architect interview angle

  • Design the API for a payments or booking service that mobile clients and AI agents will call. Strong answer: REST resources with OpenAPI, OAuth scopes, idempotency keys on every POST, rate limits per client, cursor pagination, webhooks for async results, additive changes plus a clear versioning and deprecation policy; gRPC internally between services if latency matters.
  • When would you choose GraphQL over REST? Strong answer: many client types needing different shapes of data from several back ends (e.g. a mobile app screen combining profile, orders and recommendations); mention the costs: query complexity limits, per-field auth, caching and N+1 issues; often a GraphQL layer sits in front of REST or gRPC services.

Glossary

API
Application programming interface: the contract for how software talks to software.
REST
Style built on resources (URLs) and HTTP verbs.
HTTP verbs
GET read, POST create, PUT replace, PATCH partial update, DELETE remove.
GraphQL
Query language where the client requests exactly the fields it needs from one endpoint.
gRPC
Google-originated remote procedure call framework using protobuf over HTTP/2.
Protocol buffers (protobuf)
Compact binary data format with a typed schema (.proto files).
HTTP/2
Newer HTTP version supporting many parallel streams over one connection.
Webhook
An HTTP call the provider makes to your URL when an event happens.
OpenAPI
Standard machine-readable description of a REST API.
Idempotent
Doing it twice has the same effect as doing it once.
Idempotency key
Client-generated unique id that lets the server recognise retries.
UUID (V4)
A random 128-bit identifier, practically unique.
Exponential backoff / jitter
Waiting longer after each failure / adding randomness to the wait.
Breaking change
A change that makes existing clients fail (removing or renaming fields).
Deprecation
Marking something as going away, with a timeline.
Over / under-fetching
Getting more data than needed / needing several calls to get enough.
N+1 problem
One query for a list plus one extra query per item: slow at scale.
Cursor pagination
Paging through results with an opaque 'continue from here' token.
CDN
Content delivery network: caches responses close to users.
Interceptor / filter / middleware
Code that runs around every request (auth, logging, idempotency).
