Choosing a database: SQL vs NoSQL, consistency and CAP

Track: System design fundamentals. Builds on drop 1 (scaling, caching) and drop 5 (CQRS).
Almost every architecture review ends up at the same question: where does the data live, and what happens to it when traffic grows or a machine dies? Picking the database is one of the few decisions that is expensive to undo, so a lead is expected to justify it.

NoSQL (not only SQL) is a loose label for everything that is not relational. It usually trades some flexibility of querying and strict transactions for easier horizontal scaling and flexible schemas. The modern reality is blurry: PostgreSQL stores JSON and vectors, and Spanner and Cosmos DB offer strong consistency at global scale.

How it works: replication, partitioning and the CAP trade-off

  1. Replication: copies for safety and readsEach write goes to a leader and is copied to replicas. Synchronous copying is safe but slower; asynchronous is fast but a replica can lag, so a read right after a write might show old data (eventual consistency).
  2. Partitioning (sharding): split to scale writesWhen one machine cannot hold the data or the writes, split rows by a partition key. A good key spreads load evenly; a bad one creates a hot partition where one popular key overloads one machine.
  3. CAP: the choice during a network failureWhen the network between copies breaks (Partition), a distributed database must either refuse some requests to stay correct (Consistency) or keep answering with possibly stale data (Availability). You cannot have all three during a partition. CP leans correct (Spanner, most SQL setups); AP leans always-up (Cassandra, DynamoDB default reads).
  4. PACELC: the everyday versionEven when nothing is broken (Else), you trade Latency against Consistency: waiting for copies to agree costs milliseconds. Many databases let you pick per request, e.g. DynamoDB strongly consistent reads or Cosmos DB's five consistency levels.
  5. ACID vs BASEACID (atomic, consistent, isolated, durable) transactions: all-or-nothing updates, classic in SQL. BASE (basically available, soft state, eventually consistent): accept temporary disagreement for scale.
Everyday comparison: a bank branch network vs a group chat.
A bank's branches would rather close the counter than let you withdraw the same money twice when the link to head office is down (consistent, CP). A group chat keeps letting everyone post even when someone's phone is offline; they catch up later and messages may arrive out of order (available, AP). Sharding is opening more branches, each handling customers by surname; a hot partition is the one branch next to a stadium on match day.

Trade-offs: every extra database is another thing to back up, secure, monitor and pay for. Polyglot persistence (one store per need) is right at scale, but most AI pilots should start with one managed PostgreSQL and a cache. Do not choose NoSQL because it sounds scalable if you have not written down the access patterns; do not choose SQL for a firehose of events with no relationships.

Pattern card: design around access patterns (partition key first)

What it is
List how the app reads and writes data before choosing the store, then pick a partition key that spreads load and keeps data read together, stored together.
Metaphor
Organising a library by how people actually look for books, not by the colour of the covers.
Real example
Discord partitions messages by channel id plus a time bucket so one channel's recent messages sit together (Discord engineering blog).
Use when
Any NoSQL or sharded design; any table expected to grow past one machine.
Do not use when
Small apps on one PostgreSQL instance, where normal tables and indexes are enough.
Trade-offs
Very fast for the planned queries; new kinds of questions need new indexes, duplicated tables or a separate analytics copy.
Instruction to AI / a teammate
Before picking a database, list the top five reads and writes with expected volume and consistency needs; default to managed PostgreSQL, and only propose DynamoDB or Cosmos DB with a partition key that keeps each tenant's hot data on separate partitions.

Real-world scenario and why it matters on the job

Discord (engineering blog, How Discord Stores Trillions of Messages): messages were stored in Apache Cassandra, a wide-column NoSQL database, partitioned by channel and a fixed time bucket. The cluster grew from 12 nodes in 2017 to 177 nodes with trillions of messages by early 2022. Busy servers caused hot partitions, reads were more expensive than writes, and Java garbage-collection pauses made latency unpredictable, so on-call engineers were paged often.

Their fix had two parts. They moved to ScyllaDB, a Cassandra-compatible database written in C++ (no garbage collector), and they put Rust data services between their API and the database that coalesce requests: if many users ask for the same row at once, the database is queried once. They migrated with a custom Rust migrator and ended with 72 ScyllaDB nodes instead of 177 Cassandra nodes.

Why it matters: this is the whole topic in one story. They picked a store for write-heavy, key-based access (right), the partition key created hot spots at scale (the classic risk), and the fix combined a better engine with a protective layer in front (like the caching and bulkhead patterns from drops 1 and 4). As an FDE you will be asked which database a customer pilot should use, and your answer should start from access patterns, not brand names.

FDE / architect interview angle

  • Design storage for a chat or ticketing system with 10 million users. Strong answer: write down access patterns (latest messages per channel, search, unread counts); pick a partitioned store keyed by channel plus time bucket for messages, relational for users and billing, a search index for full-text; call out hot partitions and how to mitigate them (bucketing, caching, request coalescing).
  • Explain CAP to a business stakeholder. Strong answer: when parts of the system cannot talk, we choose between refusing some actions (stay correct, e.g. payments) or answering with possibly old data (stay up, e.g. a social feed); then say which parts of their product need which, and mention the everyday latency vs consistency trade-off (PACELC).

Glossary

Relational / SQL
Database of tables with a fixed schema, queried with SQL, supporting joins and transactions.
NoSQL
Umbrella term for non-relational stores: key-value, document, wide-column, graph.
Schema
The declared structure of data (tables, columns, types).
Join
Combining rows from two tables by a shared field.
Transaction
A group of changes that succeed or fail together.
ACID
Atomic, Consistent, Isolated, Durable: the guarantees of a classic transaction.
BASE
Basically Available, Soft state, Eventually consistent: the scale-first alternative.
Replication / replica
Keeping copies of data on several machines / one of those copies.
Leader (primary)
The copy that accepts writes.
Replication lag
Delay before a replica sees a write.
Eventual consistency
Copies may disagree briefly but converge if writes stop.
Strong consistency
Every read sees the latest committed write.
Partition key / sharding
The field used to split data across machines / the act of splitting it.
Hot partition
One partition receiving far more traffic than others, overloading its machine.
CAP theorem
During a network Partition a distributed store must choose Consistency or Availability.
PACELC
Extends CAP: Else (normal times) you trade Latency vs Consistency.
Wide-column store
NoSQL design (Cassandra, Bigtable) with rows grouped by partition and sorted inside it.
Garbage collection (GC) pause
Moment a Java-style runtime stops work to free memory, causing latency spikes.
Request coalescing
Merging identical concurrent requests into one backend query.
Polyglot persistence
Using different databases for different needs in one system.
ORM
Library mapping code objects to tables (JPA, Prisma, SQLAlchemy).
Migration
A versioned script that changes the schema.
