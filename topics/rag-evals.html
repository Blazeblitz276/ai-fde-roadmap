RAG evals: how to prove your RAG is good

Track: AI/LLM systems. Focus: measuring it, so you can improve it (improving it is the follow-on topic).
'It looked fine when I tried five questions' is not an eval. An eval is a repeatable test that scores retrieval and answers separately, so when quality drops you know which half broke.

What it is and the problem it solves

A RAG answer can be wrong for two very different reasons: the retriever fetched the wrong chunks (a search problem), or it fetched the right chunks and the LLM ignored or embellished them (a generation problem). If you only look at the final answer you cannot tell which, so you end up tweaking prompts when the real fix was chunking, or vice versa. Every change (new embedding model, chunk size, prompt, model version) can silently make things worse.

RAG evaluation splits the pipeline into measurable parts and scores each one against a fixed test set (a golden set), offline before release and continuously on live traffic after release.

What you measureMetric (Ragas names in brackets)Plain question it answersNeeds a reference answer?
Retrieval: did we find it?Recall@k, hit rate (Context Recall)Of the facts needed, how many were in the retrieved chunks?Yes
Retrieval: is the top clean?Precision@k, MRR, nDCG (Context Precision)Are the relevant chunks ranked at the top, not buried?Usually
Generation: grounded?Faithfulness / groundednessIs every claim in the answer supported by the retrieved context? (low = hallucination)No
Generation: on topic?Answer / response relevancyDoes it actually answer the question asked?No
End to end: correct?Answer correctness / accuracyDoes it match the expert's answer?Yes
ProductionLatency, cost per answer, thumbs up/down, escalation rateIs it fast, affordable and trusted by users?No

How it works

  1. 1. Build a golden setCollect real user questions (from logs, support tickets, the customer's SMEs). For each: the expected answer and the source document IDs. Include hard ones: multi-hop, 'not in the docs' (correct answer is 'I don't know'), ambiguous, and recent-policy questions. Start with ~50, grow to a few hundred.
  2. 2. Score retrieval on its ownRun only the retriever. If the right doc is not in the top 5 (low recall@5), no prompt will save you: fix chunking, embeddings, hybrid search or reranking.
  3. 3. Score generation with an LLM judgeA stronger model reads question + retrieved chunks + answer and rates faithfulness (claims supported?) and relevancy. Keep each judge question narrow and binary where possible.
  4. 4. Calibrate the judgeHave humans label ~50-100 samples pass/fail, compare with the judge, fix the judge prompt until agreement is high. An uncalibrated judge is just another opinion.
  5. 5. Gate releases and watch productionRun the suite in CI on every prompt/model/index change (regression test). In production, sample conversations, judge them, and add failures to the golden set: the flywheel.
Everyday comparison: an open-book exam.
The golden set is the exam paper with an answer key. Retrieval metrics check whether the student opened the textbook at the right pages. Faithfulness checks whether what they wrote is actually on those pages, rather than made up. Relevancy checks whether they answered the question asked. The teacher marking it is the LLM judge, and calibration is a head teacher re-marking a sample to make sure the teacher grades fairly. You need all four to know if the student is good, and to know whether to fix their reading or their writing.

Benefits

  • Tells you WHERE quality broke (retrieval vs generation).
  • Lets you change models, prompts and chunking without fear (regression safety net).
  • Gives the customer numbers, not vibes: 'faithfulness 0.94, recall@5 0.88'.

Trade-offs and pitfalls

  • Golden sets take real SME time to build and go stale as documents change.
  • LLM judges cost money, can be biased (prefer long answers, their own style) and must be calibrated.
  • High scores on a narrow set can hide failures on real traffic: keep feeding production failures back in.

Pattern card: Eval-driven development (golden set + LLM-as-judge flywheel)

What it is
Treat AI quality like tests: a versioned golden set, separate retrieval and generation metrics, a calibrated LLM judge, and a release gate, fed by production failures.
Metaphor
Open-book exam with an answer key and a head teacher who re-marks samples.
Real example
DoorDash's Dasher support RAG chatbot (below).
Use when
Any RAG or agent that customers will rely on, and before every model, prompt or index change.
Do not use when
Throwaway demo; even then, keep the 20 questions you tried so they become the seed set.
Trade-offs
Confidence and speed of iteration in exchange for SME time and judge cost.
Instruction to give AI or a teammate
Build a versioned golden set of 150 questions with expected answers and source doc IDs, score recall@5 and context precision on the retriever and faithfulness plus answer relevancy with an LLM judge calibrated on 60 human labels, run it in CI on every prompt or index change, fail the build if faithfulness drops more than 2 points, and sample 2% of live traffic daily into the same dashboard.

Real company: DoorDash

DoorDash's engineering post 'Path to high-quality LLM-based Dasher support automation' describes a RAG chatbot for its delivery drivers (Dashers). The conversation is condensed into an issue summary, similar resolved cases and their knowledge-base articles are retrieved, and the LLM answers from them. Around it they built an online LLM Guardrail (a cheap semantic-similarity check between the answer and the KB article first, then an LLM evaluator for groundedness, coherence and policy compliance only if needed) and an LLM Judge that grades conversations on retrieval correctness, response accuracy, grammar, coherence to context and relevance. They report the guardrail cut hallucinations by 90% and severe compliance issues by 99%. A later DoorDash post describes an evaluation flywheel with calibrated LLM judges (precision and recall checked against human labels) used as release exit criteria.

Why it matters on the job: customers rarely ask 'is it accurate?' once; they ask after the first bad answer reaches an executive. An FDE who arrives with a golden set and a scorecard turns that conversation from blame into a fix plan.

Interview angle

  • 'Our RAG gives wrong answers. How do you debug it?' Strong answer: build or reuse a golden set; measure retrieval alone (recall@k) to see if the right chunk was even found; if yes, measure faithfulness to see if the model ignored it; fix the broken half (chunking/hybrid search/reranking vs prompt/model); re-run and compare.
  • 'How do you trust an LLM judging an LLM?' Strong answer: narrow binary judge questions, calibrate against human labels with precision/recall, use a different or stronger model, spot-check over time; DoorDash's 'verifying is easier than generating' argument.

Glossary

Eval (evaluation)
A repeatable test that scores an AI system's outputs.
Golden set
A fixed, versioned list of test questions with expected answers (and source docs).
Retriever / top-k
The search step / the k best chunks it returns.
Chunk
A piece of a document stored and searched separately.
Recall@k
Share of the needed information found in the top k results.
Precision@k
Share of the top k results that are actually relevant.
MRR / nDCG
Ranking scores that reward putting the right result near the top.
Faithfulness / groundedness
Share of the answer's claims supported by the retrieved context.
Hallucination
A confident claim not supported by the sources.
Answer relevancy
Whether the answer addresses the question asked.
LLM-as-judge
Using an LLM with a grading prompt to score outputs.
Calibration
Checking the judge against human labels and fixing it until they agree.
Regression test / release gate
Automated check that blocks a release if quality drops.
Guardrail
A check that runs on live outputs and blocks or reroutes bad ones.
Multi-hop question
One that needs facts from two or more documents combined.
SME
Subject-matter expert.
Flywheel
Loop where production failures improve the test set, which improves the system.
