What they are and the problem they solve

The classic catalogue comes from the 1994 book "Design Patterns" by the "Gang of Four". They fall into three groups: creational (how objects get created: singleton, factory), structural (how pieces fit together: adapter, decorator) and behavioural (how objects talk and choose behaviour: strategy, observer). The common goal: change one part of a system without rewriting the rest.

One running example ties all six together: an AI assistant that can use OpenAI, Azure OpenAI or Bedrock.

Pattern cards

SINGLETON: what
Exactly one instance of a class, shared everywhere.
Metaphor / example
One president / Spring beans are singletons by default (one instance per container).
Trade-offs
Saves memory and connections; but shared mutable state causes thread-safety bugs (and is the stateful smell from drop 1).
Instruction
Create the database connection pool and the loaded vision model once at startup as singletons, read-only, injected where needed, not imported as globals.
FACTORY: what
A function or class whose job is to create the right object, so callers don't use 'new SpecificThing()'.
Metaphor / example
Car dealership / Spring BeanFactory; provider-from-config helpers in LangChain.
Trade-offs
Callers stay simple and you can add types in one place; an extra layer if there's only one type.
Instruction
Add an LLM client factory that reads the provider from config and returns an object implementing our ChatModel interface.
STRATEGY: what
Define a family of interchangeable behaviours behind one interface and pick one at runtime.
Metaphor / example
Car/bike/walk in Maps / choosing GPT vs Claude vs a local model per request, or BM25 vs vector vs hybrid retrieval.
Trade-offs
No if/else chains, easy A/B tests and vendor switching; more small classes.
Instruction
Make retrieval a strategy with keyword, vector and hybrid implementations selectable per tenant in config.
ADAPTER: what
A wrapper that translates one interface into the one your code expects.
Metaphor / example
Travel plug / LangChain's per-vendor chat model classes; an anti-corruption layer around a customer's legacy SOAP API.
Trade-offs
Isolates vendor quirks so a vendor change touches one file; a thin extra layer to maintain.
Instruction
Write an adapter around the customer's legacy CRM API so the rest of our code only sees our Customer interface.
DECORATOR: what
Wrap an object or function to add behaviour before/after it, keeping the same interface.
Metaphor / example
Coffee add-ons / Python @retry and @lru_cache; Spring @Transactional, @Cacheable.
Trade-offs
Clean separation of retry/cache/logging from business logic; stacked wrappers can make debugging confusing.
Instruction
Wrap every LLM call with decorators for retry with exponential backoff, a 30-second timeout and token-cost logging; don't change the call sites.
OBSERVER: what
Subjects keep a list of subscribers and notify them when something happens (publish-subscribe inside one program).
Metaphor / example
YouTube bell / browser addEventListener, React re-rendering on state change, LLM streaming callbacks.
Trade-offs
Add listeners without touching the source; hard to trace who reacts, and leaks if listeners aren't removed. Across services this becomes pub/sub on a broker (topic 3).
Instruction
Emit an event on each agent step and let the UI stream, metrics and audit log subscribe to it independently.

Real company: Spring (VMware / Broadcom) and LangChain

The Spring Framework, the most common Java enterprise framework, is built on these patterns: its reference docs state that singleton is the default scope for beans, its container is a factory (BeanFactory), and features like @Transactional and @Cacheable work by wrapping your beans in proxies, the decorator idea. LangChain gives each model vendor its own chat-model class behind one shared interface, so swapping OpenAI for Azure OpenAI or Bedrock is a one-line change: adapter plus strategy.

Why it matters on the job: when an agentic tool generates a Spring Boot or Next.js service, it will be full of these. A lead who can say "this provider switch belongs in a strategy, not an if-chain" or "this singleton holds per-user state, that's a bug" can review AI-written code in minutes.

Where it shows up in code you'll read

tap to expand
# Python
llm = create_llm(settings.provider)          # factory -> returns a strategy
@retry(times=3) @lru_cache                    # decorators
class AzureChat(ChatModel): ...               # adapter implementing the strategy interface
bus.subscribe("step_done", update_ui)         # observer
// Java (Spring): @Service / @Component classes = singletons by default; interface ChatModel with
//   @Service("azure") / @Service("bedrock") implementations = strategies; @Transactional = decorator.
// TypeScript / Next.js: a module that exports one client instance = singleton; getProvider(name) = factory;
//   higher-order functions like withAuth(handler) = decorator; useEffect subscriptions = observer.

Interview angle

  • "Design a system that can switch LLM providers without downtime." Strong answer: strategy interface + adapters per vendor + factory from config, decorators for retry/fallback/caching, feature flag to route traffic, evals before switching.
  • "What's wrong with singletons?" Strong answer: hidden global state, thread-safety, hard to mock in tests; fine for stateless shared resources via dependency injection.

Glossary

Design pattern
A named, reusable solution to a recurring design problem.
Gang of Four (GoF)
The four authors of the 1994 book that catalogued 23 classic patterns.
Creational / structural / behavioural
Patterns about creating objects / composing them / how they interact.
Interface
A contract listing methods a class must provide, without saying how.
Instance
One concrete object created from a class.
Bean (Spring)
An object created and managed by the Spring container.
Dependency injection
Passing an object its dependencies from outside instead of it creating them.
Proxy
A stand-in object that wraps the real one to add behaviour.
Cross-cutting concern
Behaviour needed everywhere: logging, retries, auth, caching.
Thread-safety
Code that behaves correctly when many requests run at the same time.
Higher-order function
A function that takes or returns another function (how decorators work in JS/Python).
Anti-corruption layer
An adapter layer that keeps a messy external model out of your clean code.
Feature flag
A switch to turn behaviour on/off without redeploying.
