Load balancing and consistent hashing

Track: System design fundamentals. Builds on drop 1 (horizontal scaling, stateless services), drop 3 (API gateway, circuit breaker) and drop 8 (sharding, hot partitions).
In drop 1 you scaled out by adding more identical servers. Two questions follow immediately: who decides which server gets each request, and what if a request must go to one particular server because that server holds the user's data or session? Load balancing answers the first, consistent hashing the second.

What it is and the problem it solves

A load balancer is a single front door that spreads incoming requests across a pool of servers, stops sending traffic to servers that are unhealthy, and lets you add or remove servers without clients noticing. Without it, one server gets overloaded while others sit idle, and any server crash becomes a user-facing outage.

Consistent hashing is a way to map a key (user id, chat channel, cache key, document id) to one server so that the same key always lands on the same server, and when a server is added or removed only a small slice of keys move. A naive approach (hash the key, divide by the number of servers, take the remainder) reshuffles almost every key whenever the server count changes, which empties caches and floods databases.

How it works

  1. Pick a server (algorithm)Round robin (take turns), least connections (whoever is least busy), weighted (bigger servers get more), or hash-based (same client or key -> same server).
  2. Health checksThe balancer pings each server (for example GET /health every 10 s). After a few failures it stops sending traffic there; after a few successes it adds it back. This is what makes rolling deploys and auto-scaling safe.
  3. Sticky sessions (session affinity)A cookie pins a user to one server. Handy for legacy apps that keep login state in memory, but it breaks even spreading and loses sessions when that server dies. The better fix is stateless servers with sessions in Redis (drop 1).
  4. Consistent hashing: the ringImagine a clock face numbered 0 to a very large number. Each server is hashed to a few points on the clock. Each key is hashed to a point and walks clockwise to the first server it meets. Add a server: it only takes keys from its clockwise neighbour. Remove one: only its keys move to the next server.
  5. Virtual nodesEach physical server is placed on the ring many times (hundreds) so keys spread evenly and a failed server's load is shared by many neighbours, not dumped on one.
Everyday comparison: a supermarket's billing counters and a school's locker rows.
The load balancer is the staff member at the front waving you to the shortest open counter, and closing a counter when the cashier is on break (health check). Consistent hashing is how a school assigns lockers by the first letter of your name around a circular corridor: when a new locker block opens between M and P, only students N and O move; everyone else keeps their locker. With the naive method, opening one block would make every student change lockers.

When to use / when not to use

Solid arrows = yes, dashed = no. A single small app on a serverless platform (Cloud Run, Container Apps) already has a managed balancer built in; you do not add one yourself.

Pattern card: consistent-hash routing

What it is
Route each key to an owning node via a hash ring with virtual nodes, so the same key always lands on the same node and scaling moves only a small share of keys.
Metaphor
Lockers assigned around a circular corridor: a new locker block only affects the neighbours next to it.
Real example
Discord routes guilds (servers) and sessions to Elixir nodes with a consistent hash ring; Amazon DynamoDB's ancestor, the 2007 Dynamo paper, popularised the idea for databases.
Use when
Distributed caches, chat/presence servers, partitioned stores, sharded queues, anything keeping per-key state in memory.
Do not use when
Servers are stateless (plain balancing is simpler) or a managed service already does it for you (DynamoDB, Cosmos DB, Redis Cluster).
Trade-offs
Stable placement and warm caches vs extra complexity, ring-membership coordination, and hot keys that still need special handling.
Instruction to AI / a teammate
Put the API behind a managed L7 load balancer with /health checks and no sticky sessions, and route per-tenant cache and websocket state with a consistent hash ring (about 200 virtual nodes per server) so adding a node moves only its share of tenants.

Real-world scenario: Discord

Discord's engineering post \"How Discord Scaled Elixir to 5,000,000 Concurrent Users\" (July 2017) states plainly that Discord is a distributed system achieved through consistent hashing: a ring data structure looks up which node owns a particular entity (such as a guild). Each session node could hold up to 500,000 live sessions, and an average user is in 5 guilds, so on reconnect bursts every session looked up the ring several times. The single process guarding the ring became a bottleneck (about 12 microseconds per request/reply, roughly 30 seconds of lookups after a session server restart), so they rewrote the ring in pure Elixir and made reads almost free with a shared read-only copy (their FastGlobal library). Their open-source ExHashRing library, described as in production at Discord, uses 512 virtual nodes per member by default.

Why it matters on the job
In customer architectures you will meet websockets, chat, per-tenant caches and GPU inference servers holding models or KV caches in memory. Knowing that the ring itself can become a hot path, and that virtual nodes smooth out load, lets you spot a scaling cliff before the customer's launch day.

FDE / architect interview angle

  • Design a chat or live-notification service for 5 million concurrent users. Strong answer: global DNS / L7 balancer to the nearest region, websocket gateways behind an L4/L7 balancer with health checks and connection draining, consistent hashing from channel id to the server holding that channel's state, virtual nodes for even spread, a plan for hot channels (split or fan out), and what happens on node failure and reconnect storms.
  • Why not just use hash(key) % N? Strong answer: changing N remaps nearly every key, so every cache misses at once and the database is flooded (thundering herd); consistent hashing moves only about 1/N of keys, and virtual nodes keep the spread even.

Glossary

Load balancer
A component that spreads requests across a pool of servers and skips unhealthy ones.
L4 / L7
Network layers: L4 sees only addresses and ports; L7 sees the HTTP request itself.
TLS termination
The balancer decrypts HTTPS so servers behind it receive plain requests.
WAF
Web application firewall: blocks common attacks at the L7 balancer.
Health check
A regular probe (such as GET /health) that decides whether a server gets traffic.
Connection draining
Letting in-flight requests finish before removing a server.
Round robin / least connections
Take turns / send to the least busy server.
Sticky session (affinity)
Pinning a user to one server, usually with a cookie.
Hash
A function that turns any input into a fixed-size number, the same input always giving the same number.
Hash ring
The circle of hash values on which servers and keys are placed.
Virtual node
One of many positions a physical server occupies on the ring.
Hot key
One key so popular it overloads its owning node.
Thundering herd / cache stampede
Many requests hitting the database at once because caches missed together.
Guild
Discord's internal name for a server (community).
Elixir / Erlang VM
A language and runtime built for huge numbers of lightweight concurrent processes.
Service mesh / Envoy
A layer of proxies (sidecars, drop 4) that handles routing, retries and balancing between services.
