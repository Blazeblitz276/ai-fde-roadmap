CI/CD and infrastructure as code: Terraform vs Bicep vs CDK

Track: Production & ops + Cloud. Ties to drop 5 (hosting an app on Azure and AWS) and drop 4 (monitoring).
CI/CD is the automatic conveyor belt that takes a code change, tests it, and ships it. Infrastructure as code (IaC) means the cloud resources themselves (databases, container apps, networks, IAM roles) are described in files kept in git, instead of being clicked together in a console. Together they make every change reviewable, repeatable and reversible.

How it works

  1. Change in gitApp code and infrastructure files live in the repo. A coding agent can write both; the pull request is where a human checks them.
  2. CI checksA pipeline (GitHub Actions, Azure DevOps Pipelines, AWS CodePipeline, Google Cloud Build) builds the app, runs unit tests, linting, dependency and secret scans, and for AI apps the eval golden set (topic 1) and injection tests (topic 3). For IaC it runs 'plan' and posts the diff on the PR.
  3. Package onceBuild one container image, tag it with the commit id, push to a registry (ECR, Azure Container Registry, Artifact Registry). The same image goes to every environment.
  4. Deploy to stagingIaC 'apply' makes staging match the files; the image is deployed; automated smoke tests run.
  5. Promote to production safelyManual approval or automated canary: send a few percent of traffic to the new version, compare error rates and latency with the old one (drop 4 golden signals), then roll forward or roll back automatically.
Everyday comparison: an architect's blueprint and a car factory line.
IaC is the blueprint for a house: instead of telling builders 'add a window here' over the phone (console clicks), you change the drawing, everyone reviews it, and the builder makes the house match the drawing; you can build an identical second house (staging) from the same drawing. CI/CD is the car factory line: every car passes the same quality stations in order, and a few cars are road-tested (canary) before the full batch ships.

When to use / when not to use

Solid arrows = yes, dashed = no. CI is worth it from day one on any shared repo; full continuous deployment to production needs good tests and monitoring first, otherwise use continuous delivery with a manual approve button.

ChoiceBenefitCost
IaC vs consoleRepeatable, reviewable, rebuild after disaster, audit trailLearning curve; someone 'fixing' things in the console causes drift
Continuous deployment vs manual releaseSmall, frequent, low-risk changesNeeds strong tests, monitoring, rollback
One shared pipeline template vs each team's ownConsistency and security by defaultLess flexibility

Pattern card: GitOps-style plan-on-PR, apply-on-merge

What it is
All infrastructure and deploy changes go through a pull request that shows the IaC plan; merging triggers apply, environment by environment.
Metaphor
Changing the blueprint with a sign-off, then the builder follows it, first on the show-home, then on the real house.
Real example
Slack's Terraform pipelines (below).
Use when
Any team past a prototype; regulated customers who need an audit trail.
Do not use when
A throwaway one-day spike; even then, delete it afterwards.
Trade-offs
Slower than a quick console fix in an emergency; you need a break-glass process.
Instruction to AI / a teammate
Write Terraform for the Container App, Postgres and Key Vault in dev, staging and prod, store state in an Azure Storage backend with locking, and add a GitHub Actions workflow that posts 'terraform plan' on every PR, blocks merge if the plan or the eval suite fails, applies to staging on merge, and needs a manual approval for prod.

Real-world scenario and why it matters on the job

Slack ('How We Use Terraform At Slack', Slack Engineering, Oct 2022): Slack manages infrastructure on AWS, GCP, DigitalOcean and NS1 with Terraform, choosing it over AWS-native CloudFormation so one tool and syntax covers every provider. Merging a change to a Terraform state file triggers a Jenkins pipeline with two stages, plan then apply; state files are chained so changes must be applied to sandbox and development before production; the plan output is posted on the pull request for reviewers, and CI blocks merges with broken Terraform plans.

Netflix open-sourced Spinnaker, its multi-cloud continuous delivery platform, in November 2015, and in 2018 released Kayenta with Google: automated canary analysis that compares the new version's metrics against the old one and can promote or fail a deploy automatically.

Why it matters: when you hand an AI-built app to a customer (drop 5), 'here is the repo with Terraform/Bicep and the pipeline' is what makes it production and not a demo. Your coding agents will happily generate IaC; your job as lead is to know what to ask for (environments, state backend, plan on PR, approvals, secrets in a vault) and to read the plan before approving.

on: pull_request -> jobs: test, run evals, terraform plan (comment on PR)
on: push to main -> jobs: build image, terraform apply (staging), deploy, smoke test
                 -> prod: wait for manual approval, then apply + deploy

FDE / architect interview angle

  • 'Terraform or Bicep for an Azure customer?' Strong answer: Bicep if they are Azure-only and want the simplest native path with no state file; Terraform if they are multi-cloud, use SaaS providers, or the team already knows it; mention state storage and locking, drift, and the BSL licence / OpenTofu question for some enterprises.
  • 'Design a CI/CD pipeline for an LLM app.' Strong answer: standard build/test/scan, plus prompt and model versions tracked in git, eval golden set and injection tests as merge gates, one image promoted through environments, IaC plan on PR, canary rollout watched on quality, latency and cost metrics, fast rollback.

Glossary

CI
Continuous integration: automatic build and tests on every change.
CD
Continuous delivery (ready to release with a click) or deployment (released automatically).
Pipeline
The ordered list of automated steps a change goes through.
IaC
Infrastructure as code: cloud resources defined in versioned files.
Declarative
You describe the end state you want; the tool works out the steps.
HCL
HashiCorp Configuration Language, Terraform's file format.
ARM template
Azure Resource Manager's JSON format; Bicep compiles into it.
CloudFormation
AWS's native IaC service; CDK generates its templates.
State file
Terraform's record of what it created, compared against your files to plan changes.
Locking
Preventing two people from applying changes to the same state at once.
Drift
When real infrastructure no longer matches the IaC files (usually from console edits).
Plan / apply
Preview the changes / carry them out.
Artifact / container image
The packaged build that gets deployed; same one in every environment.
Registry
Storage for container images (ECR, ACR, Artifact Registry).
Staging
A production-like environment for final testing.
Canary release
Sending a small share of traffic to a new version first and comparing its health.
Rollback
Returning to the previous working version.
GitOps
Using git pull requests as the single way to change infrastructure and deployments.
BSL / OpenTofu
Terraform's 2023 source-available licence / the open-source community fork.
Break-glass
A controlled emergency process to bypass the normal pipeline.
