Logging and monitoring: CloudWatch vs Azure Monitor vs GCP Cloud Logging

Track: Production and ops + Cloud. This is the full picture: what to record, where it goes on each cloud, and how you find a problem fast.
Observability is being able to answer 'what is going wrong, for whom, and why' from the outside of a running system, using three signals: logs, metrics and traces.

What it is and the problem it solves

Your AI app is live. A customer says 'it was slow and gave a weird answer around 3 pm'. Without observability you are guessing. With it, you search by their user ID, see the request took 14 s, the trace shows 11 s in the reranker call, the log shows the LLM got 3 chunks instead of 8, and a metric shows reranker latency spiked for everyone at 2:55 pm after a deploy.

SignalPictureAnswersExample
LogsDiary entries with timestampsWhat exactly happened in this request?{level: ERROR, request_id: r-81, user: u-12, msg: 'reranker timeout'}
MetricsDashboard gauges over timeIs the system healthy right now, and is it getting worse?p95 latency, error rate, requests/s, tokens/min, queue depth
TracesA parcel's tracking history across depotsWhere did the time go across services?API 14 s = retrieve 1.2 s + rerank 11 s + LLM 1.8 s

How it works

  1. 1. Log structured, not proseWrite logs as JSON fields (level, request_id, tenant, route, latency_ms, model, tokens_in/out) rather than free sentences, so you can filter and count. Never log secrets; mask personal data and be deliberate about logging prompts.
  2. 2. One ID across everythingA correlation / trace ID is created at the edge and passed through every service, queue message and LLM call, so one search shows the whole story.
  3. 3. Metrics on the four golden signalsGoogle's SRE book: latency, traffic, errors, saturation. For AI apps add tokens per request, cost per request, cache hit rate, retrieval recall from sampled evals.
  4. 4. Traces for the pathEach step (API, retrieve, rerank, LLM, tool call) is a span with start/end time; together they form a trace. OpenTelemetry has GenAI conventions, and Azure AI Foundry, Bedrock and Vertex can emit agent/LLM traces.
  5. 5. Alert on symptoms users feelPage someone for 'error rate above 2% for 5 min' or 'p95 above 8 s', not for 'CPU 80%'. Route alerts to the owning team with a runbook link.
Everyday comparison: a hospital patient.
Metrics are the bedside monitor (heart rate, blood pressure) that beeps when something is off. Logs are the nurses' notes: exactly what was done and when. Traces are the patient's journey through reception, X-ray, lab and ward with time spent in each. The correlation ID is the patient's wristband that links them all.

Benefits

  • Find and fix incidents in minutes instead of hours.
  • Proves SLOs and AI quality to the customer with data.
  • Shows cost drivers (tokens, retries) per tenant and feature.

Trade-offs

  • Ingestion and retention cost real money; logs are a classic surprise line on the bill (drop 3 topic 4).
  • Logs can leak secrets or personal data if you are careless.
  • Too many alerts cause alert fatigue; people start ignoring pages.

Pattern card: Observability by default (logs + metrics + traces with one correlation ID)

What it is
Every service emits structured logs, golden-signal metrics and traces through OpenTelemetry, all tagged with the same request ID, and alerts fire on user-facing symptoms.
Metaphor
Hospital monitor, nurses' notes and the patient's wristband.
Real example
Uber's logging platform and Google's SRE golden signals (below).
Use when
Anything going to production, and especially multi-step AI or agent flows where failures hide between steps.
Do not use when
Throwaway spikes; even then keep a request ID and error logging.
Trade-offs
Faster debugging and proof of quality vs ingestion cost, privacy care and alert tuning.
Instruction to give AI or a teammate
Add OpenTelemetry to the Next.js API and the Python worker exporting to Application Insights, log JSON with request_id, tenant_id, model, tokens and latency_ms (no prompts or PII), create spans for retrieve, rerank and LLM, and set alerts for error rate above 2% and p95 latency above 8 s over 5 minutes, with 30-day retention.

Real companies: Uber and Google

Uber's engineering post 'Fast and Reliable Schema-Agnostic Log Analytics Platform' (2021) describes outgrowing the ELK stack it started with in 2014: they had to run 20+ Elasticsearch clusters per region to limit blast radius, and log fields that changed type broke ingestion. They rebuilt on ClickHouse, ingesting millions of logs per second from thousands of services across regions and storing several petabytes, with logs tagged by rich key-value context (like request ID) so engineers can slice and dice.

Google's SRE book chapter 'Monitoring Distributed Systems' defines the four golden signals (latency, traffic, errors, saturation) and argues that pages should fire on symptoms users notice. Most cloud dashboards and SLO tools follow this model.

Why it matters on the job: in customer deployments the FDE is often first on the call when something breaks. Being able to say 'here is the trace, here is the failing step, here is the fix' builds trust fast, and observability requirements (retention, PII) often come up in security reviews.

Interview angle

  • 'Users say the AI assistant is slow. How do you investigate?' Strong answer: check golden-signal dashboards for when and who, find a slow trace, see which span dominates (retrieval, rerank, LLM, tool), correlate with deploys or provider status, check saturation (quotas, queue depth), fix and add an alert so it is caught before users notice.
  • 'What would you monitor for an LLM app beyond normal web metrics?' Strong answer: tokens and cost per request/tenant, latency per step, 429s from the provider, cache hit rate, guardrail blocks, sampled faithfulness/quality scores, user feedback, and model/prompt version on every log line.

Glossary

Observability
How well you can understand a system's internal state from what it emits.
Structured logging
Logs written as key-value fields (usually JSON) instead of free text.
Log level
Severity label: DEBUG, INFO, WARN, ERROR.
Metric
A number measured over time (count, gauge, histogram).
p95 latency
95% of requests are faster than this value; captures the slow tail better than an average.
Trace / span
A trace is one request's full journey; a span is one timed step inside it.
Correlation ID / request ID / trace ID
An identifier passed along with a request so all its logs and spans can be linked.
Four golden signals
Latency, traffic, errors, saturation (Google SRE).
Saturation
How full your most constrained resource is (CPU, memory, quota, queue).
SLO / SLI
Service Level Objective (target, e.g. 99.5% of requests under 3 s) measured by a Service Level Indicator.
OpenTelemetry (OTel)
Open standard and SDKs for emitting logs, metrics and traces to any backend.
APM
Application Performance Monitoring: tools that combine traces, metrics and errors per app (Application Insights, X-Ray).
KQL
Kusto Query Language, used in Azure Log Analytics and Application Insights.
Log Analytics workspace
Azure's store for logs that you query with KQL.
Logs Insights / Logs Explorer
The log search consoles of AWS CloudWatch and GCP Cloud Logging.
ELK
Elasticsearch, Logstash, Kibana: a popular self-hosted logging stack.
ClickHouse
A fast column-oriented analytics database.
Retention / sampling
How long data is kept; keeping only a fraction of traces or logs to control cost.
PII
Personally identifiable information (names, emails, phone numbers, IDs).
Alert fatigue
Too many noisy alerts, so real ones get ignored.
