System design from zero: requests, latency, scaling, stateless services

What it is and the problem it solves

A client (browser, mobile app, another service, or an AI agent) sends a request over the network. A server runs your code, usually talks to a database, and sends a response back. That is the client-server model. The design problem starts when traffic grows: one server runs out of CPU, memory or connections, responses slow down, and if that single server dies the whole product is down.

Two numbers describe how a system feels under load. Latency is how long one request takes, start to finish (for example 120 ms). Throughput is how many requests the system finishes per second (for example 5,000 requests per second). They are different: a highway can have a high speed limit (low latency) but only one lane (low throughput).

There are two ways to grow. Vertical scaling (scale up) means buying a bigger machine: more CPU and RAM. Horizontal scaling (scale out) means adding more machines of the same size behind a load balancer. Horizontal scaling only works cleanly if the servers are stateless: no server keeps anything about a user in its own memory between requests, so any server can handle any request.

How it works

  1. Request arrivesThe user's request hits the load balancer, not a specific server.
  2. Load balancer picks a serverRound robin or least-busy. It also stops sending traffic to servers that fail health checks.
  3. Server does the workIt reads anything it needs about the user (session, cart, profile) from shared storage, never from its own memory.
  4. Response goes backThe server forgets the request. The next request from the same user can land on a different server and still work.
  5. Traffic spikesAutoscaling adds identical servers; when traffic drops it removes them. Because they are stateless, nothing is lost.
Everyday comparison: a bank with many tellers.
One brilliant teller is vertical scaling: you can make them faster, but there is a limit and a single sick day closes the bank. Many tellers is horizontal scaling. It only works because your account details live in the bank's central system, not in one teller's head. Any teller can serve you: that is what stateless means. The queue manager who sends you to the next free counter is the load balancer.

Benefits of stateless + scale out

  • Near-unlimited growth by adding machines.
  • No single server is critical, so failures are survivable.
  • Deploys are easy: replace servers one at a time (rolling deploy).

Costs and trade-offs

  • State has to live somewhere shared (DB, Redis), which becomes the new bottleneck to design for.
  • More moving parts: load balancer, health checks, autoscaling rules.
  • Network hops to shared state add a little latency to every request.

Pattern card: stateless service behind a load balancer

What it is
Identical app servers that keep no per-user memory, behind a load balancer, with state in shared storage.
Metaphor
Bank tellers sharing one central account system.
Real example
Netflix, after its 2008 database outage, moved to AWS and rebuilt around stateless services so any instance can serve any request.
Use when
Traffic is unpredictable, uptime matters, or you want rolling deploys.
Do not use when
A tiny internal tool on one box is enough, or the workload is inherently stateful (a database, a long-lived game session) and needs a different pattern.
Trade-offs
Scale and resilience in exchange for a shared state store and more infrastructure.
Instruction to give AI or a teammate
Make the API stateless: no session data in server memory, store sessions in Redis and data in Postgres, run at least two instances behind a load balancer with health checks and autoscaling.

Real company: Netflix

In August 2008 a major database corruption stopped Netflix from shipping DVDs for three days. Netflix wrote that this is when it decided to move away from "vertically scaled single points of failure, like relational databases in our datacenter, towards highly reliable, horizontally scalable, distributed systems in the cloud". It completed the move to AWS in January 2016. Its 2011 tech-blog post on surviving an AWS outage names stateless services as a major design goal: any instance can serve any request, so a failed server is replaced automatically.

Why it matters on the job: as an FDE you will often inherit a customer's AI prototype that runs on one VM and keeps conversation history in memory. The first production question is "what happens with two copies of this, or when this box restarts?" Spotting that is this topic.

Where it shows up in code you'll read

tap to expand

The tell-tale sign of a stateful server is user data stored in a variable that lives as long as the server. The stateless version reads and writes it in shared storage.

# Python (FastAPI) - stateful: breaks with 2 servers
chat_history = {}            # lives in THIS server's memory

# stateless: any server can answer
history = redis.get(f"chat:{user_id}")
// Java (Spring Boot): the same smell is a field on a @Service holding a Map of users.
// Fix: Spring Session backed by Redis, data in the database.

// Next.js: API routes / server actions on Vercel or Lambda are stateless by design,
// so a module-level variable can silently "forget" between requests.

Interview angle

  • "Our app is slow under load. How do you scale it?" Strong answer: measure first (is it CPU, DB, or network?), make the app tier stateless, put it behind a load balancer with autoscaling, then look at the database (read replicas, caching) because that is usually the next bottleneck.
  • "Latency vs throughput?" Strong answer: define both with units, give an example where improving one hurts the other (batching GPU inference raises throughput but adds latency per image), and tie it to what the user or SLA actually needs.

Glossary

Client / server
The asker and the answerer. A client sends a request; a server processes it and replies.
Request / response
One message asking for something (e.g. HTTP GET /orders) and the reply.
Latency
Time for one request, usually in milliseconds (ms).
Throughput
Work completed per unit of time, e.g. requests per second (RPS).
Vertical scaling
Making one machine bigger.
Horizontal scaling
Adding more machines of the same kind.
Load balancer
A component that spreads incoming requests across servers and skips unhealthy ones.
Health check
A periodic ping the load balancer sends to see if a server is alive.
Autoscaling
Automatically adding or removing servers based on load.
Stateless / stateful
Stateless: keeps nothing about a user between requests. Stateful: does, so the user must return to the same server.
Session
Data about a logged-in user's visit (login, cart, chat history).
Single point of failure
One component whose failure takes the whole system down.
Rolling deploy
Updating servers a few at a time so the service never goes fully offline.
Redis
A very fast in-memory data store, often used for sessions and caching.
SLA
Service level agreement: the promised uptime or speed.
