Multi-tenancy for SaaS and AI apps: silo vs pool vs bridge on Azure and AWS

Track: System design + Cloud. Builds on drop 1 (IAM), drop 3 (cost control), drop 8 (choosing a database) and drop 9 (networking).
As soon as an FDE pilot becomes a product sold to a second customer, the question is: do customers share the same servers and database, or each get their own? That choice drives cost, security reviews and how hard enterprise deals are to close.

What it is and the problem it solves

A tenant is one customer organisation using your software. Multi-tenancy means one product serves many tenants. The hard part is tenant isolation: tenant A must never see tenant B's data, and a noisy tenant must not slow everyone else down (the noisy neighbour problem), while keeping cost per tenant low enough to make money.

Model (AWS terms)What is sharedAzure Architecture Center equivalentBest for
SiloNothing: each tenant gets its own stack (account/subscription, database, sometimes model deployment)Single-tenant deployments (often using the Deployment Stamps pattern)Regulated or very large customers; strict data residency
PoolEverything: shared compute and database, rows tagged with tenant_idFully multitenant deploymentsMany small customers, self-service SaaS, lowest cost
Bridge (hybrid)Some layers shared, others dedicated (e.g. shared web tier, per-tenant database or index)Vertically / horizontally partitioned deploymentsMixed customer base; premium tier gets dedicated pieces

How it works

  1. Identify the tenant on every requestThe tenant id comes from the signed-in token (drop 7), never from a form field the client can change.
  2. Enforce isolation in layersPool: every query filtered by tenant (database row-level security, partition keys, search filters); credentials scoped to that tenant. Silo: separate databases, accounts/subscriptions, networks.
  3. Isolate the AI parts tooPer-tenant vector indexes or mandatory tenant filters in RAG, per-tenant prompt/semantic cache keys, per-tenant token quotas so one customer cannot burn shared model capacity.
  4. Meter and route by tierRecord usage per tenant for billing and cost; onboard premium tenants into dedicated stamps without changing the app code.
Everyday comparison: places to live
Silo is independent houses: total privacy, each with its own water tank and bill, expensive. Pool is a hostel dorm: cheapest, shared everything, and one loud roommate disturbs all. Bridge is an apartment complex: shared lobby, lifts and security, but each flat has its own lock and meter.

When to use / when not to use

Solid arrows = yes, dashed = no.

ModelBenefitsCosts / risks
SiloStrongest isolation, easy security story, per-tenant customisation, no noisy neighboursHighest cost per tenant, slow onboarding, upgrading 200 stacks, cloud limits on accounts/resources
PoolCheapest, fastest onboarding, one deployment to upgradeOne missing tenant filter = data leak across customers; noisy neighbours; harder per-tenant cost attribution
BridgeBalance cost and isolation; sell tiersTwo operating models to run; routing and automation complexity

Real-world scenario (verified)

Salesforce (pool model at huge scale)
Salesforce's published 'Force.com Multitenant Architecture' white paper and its Architects site describe a shared, metadata-driven platform: every customer's records live in shared tables tagged with an OrgID, custom objects and fields are metadata rather than separate schemas, and data and indexes are partitioned by OrgID so queries only touch one org's data. Thousands of companies share one platform, which is why upgrades roll out to everyone at once.
AWS and Azure guidance
AWS's 'SaaS Tenant Isolation Strategies' whitepaper defines silo, pool and bridge and recommends choosing per service; Azure Architecture Center's 'Tenancy models for a multitenant solution' covers the same spectrum, from fully multitenant to single-tenant deployments.
Why it matters on the job
Enterprise customers' security reviews ask 'how is our data isolated from other customers, including in your vector index and LLM logs?'. An FDE who can explain the tenancy model, show the isolation controls and offer a dedicated tier unblocks deals.

Pattern card: tiered tenancy (bridge)

What it is
Pool most tenants on shared infrastructure, and give tenants that need it dedicated data, index or model pieces, all behind one tenant-aware entry point.
Metaphor
Apartment complex with shared lobby, private flats and a few independent villas in the same gated community.
Real example
Salesforce's OrgID-partitioned shared platform (pool); AWS SaaS whitepaper bridge model; Azure Deployment Stamps for dedicated tiers.
Use when
B2B SaaS or AI products with a mix of small customers and regulated enterprises.
Do not use when
Internal single-company tools (one tenant), or a handful of huge customers who all need silos.
Trade-offs
Cost efficiency plus enterprise-grade isolation on demand vs two ways of operating and more automation.
Instruction to AI / a teammate
Make every request carry tenant_id from the auth token, enforce it with row-level security, tenant-filtered vector search, tenant-prefixed cache keys and per-tenant token quotas, and add a deployment stamp path so an enterprise tenant can get its own database and model deployment without code changes.

FDE / architect interview angle

  • Design a multi-tenant RAG assistant for 500 small firms and 5 banks. Strong answer: bridge model; pooled app tier and shared index with mandatory tenant filters for small firms; dedicated index, database, keys and possibly region/model deployment for banks; tenant id from the token; per-tenant quotas, cache keys and cost metering; isolation tests in CI that try cross-tenant access.
  • How do you stop one tenant from eating everyone's LLM capacity? Strong answer: per-tenant rate limits and token budgets at the gateway (drop 3 token bucket), queues for bulk jobs, separate deployments or provisioned capacity for premium tiers, and alerts on per-tenant spend.

Glossary

Tenant
One customer organisation using a shared product.
Multi-tenancy
One deployment of software serving many tenants.
Tenant isolation
Controls that keep tenants' data and performance separate.
Silo / pool / bridge
Dedicated per tenant / fully shared / a mix of both (AWS terms).
Noisy neighbour
A tenant whose heavy use slows down others on shared resources.
Row-level security (RLS)
A database feature that automatically filters rows to the current tenant.
Partition key
The field (often tenant_id) a database uses to spread and group data.
Deployment Stamps
An Azure pattern of repeating identical copies of the full stack, each serving a group of tenants.
Subscription / account
Azure's and AWS's billing and isolation boundaries for resources.
Data residency
A requirement that data stays in a specific country or region.
Metering
Recording each tenant's usage so you can bill and track cost.
Token quota / rate limit
A cap on how many LLM tokens or requests a tenant can use per period.
OrgID
Salesforce's identifier for a customer org, used to tag and partition all its data.
Metadata-driven
Customer customisations stored as configuration data rather than separate code or schemas.
