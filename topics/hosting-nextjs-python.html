Hosting an AI-built Next.js + Python app end to end on Azure and AWS

Track: Cloud + FDE craft. This ties together drop 1 (IAM), drop 3 (cost), drop 4 (logging, serverless containers).
The typical app an agentic coding tool builds for you: a Next.js frontend (with server-side rendering and API routes), a Python backend (FastAPI) that calls an LLM and maybe a vector index, a Postgres database, file storage and some secrets. Here is one sensible MVP path and the production upgrades, on both clouds.

What it is and the problem it solves

'It works on my laptop' is not a product. Hosting end to end means: where each piece runs, how it gets secrets and permissions without hard-coded keys, how code gets from GitHub to the cloud automatically, how you see errors and cost, and how it scales and stays secure. As an FDE, this is the path from demo to something a customer's security team will sign off.

How it works: reference architecture

  1. 1. Containerise the backendDockerfile for the Python API; no local files or in-memory sessions (stateless, drop 1); health endpoint.
  2. 2. Pick the frontend hostAWS Amplify Hosting auto-detects Next.js SSR (versions 12-15; no Next.js streaming or edge middleware). On Azure, Static Web Apps' hybrid Next.js support is still preview with a 250 MB app limit, so for a full server-rendered app use App Service or Container Apps (Next.js 'standalone' container).
  3. 3. Data and AI servicesManaged Postgres (with pgvector if you need simple vector search), object storage for uploads, and the managed LLM endpoint in the same region.
  4. 4. Identity and secretsManaged identity / IAM role for the API to reach the LLM, DB and storage; remaining secrets in Key Vault / Secrets Manager. No keys in code or .env in git.
  5. 5. CI/CDGitHub Actions: test, build image, push to ACR/ECR, deploy. Use OIDC federation so GitHub gets short-lived cloud credentials instead of stored keys. Describe the infra in Bicep/Terraform/CDK.
  6. 6. OperateOpenTelemetry traces with request IDs (drop 4), alerts on error rate and latency, budgets and tags per environment (drop 3), separate dev and prod.
Everyday comparison: opening a restaurant.
The recipe working in your home kitchen is the local app. Hosting is renting the shop (compute), the walk-in fridge (database, storage), the locked cash box with staff badges (secrets, identity), a supplier delivery schedule (CI/CD), CCTV and the till report (monitoring, budgets), and a health inspection (security review) before opening day.

Benefits of this managed path

  • No servers to patch; HTTPS, scaling and deploy history built in.
  • Identity-based access (no keys) satisfies most security reviews.
  • Containers keep the option to move to Kubernetes or another cloud.

Trade-offs

  • Platform limits (Amplify: no Next.js streaming; SWA hybrid still preview) can bite AI chat UIs that stream tokens; test streaming early.
  • Scale-to-zero means cold starts on the first request.
  • More moving parts than one VM: needs IaC and naming/tagging discipline.

Pattern card: MVP-to-production landing path

What it is
A repeatable template: containerised stateless services on a managed platform, managed data and AI services, identity instead of keys, IaC + CI/CD, observability and budgets from day one.
Metaphor
A franchise kit: every new shop opens with the same layout, safe, CCTV and supplier contracts.
Real example
Aon built AonGPT on Azure using Foundry, Azure Container Apps (serverless), Cosmos DB for chat history and Azure PostgreSQL for role-based access; Microsoft's Nov 2025 customer story reports 62,000+ users onboarded and 6.4M+ messages.
Use when
Any customer pilot that may go to production; internal AI tools.
Do not use when
A throwaway demo for one meeting (a single container or local run is fine), or the customer mandates their own platform (deploy onto it).
Trade-offs
Higher setup effort on day one; pays back at the first security review and first incident.
Instruction to AI / a teammate
Write Bicep for a dev and prod environment with Container Apps for the FastAPI backend and Next.js frontend, Azure Database for PostgreSQL, Key Vault and Application Insights, give the backend a managed identity with access only to Azure OpenAI and the database, and add a GitHub Actions workflow using OIDC that builds, pushes to ACR and deploys on merge to main.

Real-world scenario and why it matters on the job

Aon (global risk and HR services firm) needed a secure, governed AI assistant across teams. Per Microsoft's customer story, AonGPT runs on serverless Azure Container Apps for performance and reliability, stores chat data in Cosmos DB, uses Azure PostgreSQL for role-based access control, grounds answers with Bing Search through Foundry Agent Service, and uses Document Intelligence for a policy-comparison tool that replaced work taking up to 40 hours. Aon reports 62,000+ users with access and about 31,000 monthly active users. That is exactly the shape of the reference architecture above.

On the job: FDE interviews and customer kick-offs both start with 'how would you get this into production on our cloud?'. Being able to draw this diagram for Azure and AWS, name the security pieces (identity, secrets, private networking) and the operating pieces (CI/CD, monitoring, budgets) is the core of the role.

FDE / architect interview angle

  • 'Walk me through deploying this AI app to production on Azure (or AWS).' Strong answer: the diagram above, then identity (managed identity / IAM roles), secrets, private networking for DB and LLM, IaC + CI/CD with OIDC, observability with request IDs, budgets, environments, and a rollback plan.
  • 'The chat UI does not stream on our host. Why?' Strong answer: check the platform's streaming support (e.g. Amplify does not support Next.js streaming), proxies that buffer responses, and timeouts; move the streaming endpoint to a container host if needed.

Glossary

SSR (server-side rendering)
The server builds each page's HTML on request, instead of only shipping static files.
Streaming
Sending the response in pieces as it is generated (how chat UIs show tokens appearing).
Edge middleware
Small code that runs on CDN servers close to users before a request reaches your app.
FastAPI
A popular Python framework for building web APIs.
Managed identity / IAM role
A cloud-issued identity for your app so it can access services without stored keys.
Key Vault / Secrets Manager
Managed safes for passwords, keys and connection strings.
OIDC federation
Letting GitHub Actions prove who it is to the cloud and get short-lived credentials, with no stored secrets.
CI/CD
Continuous integration / continuous delivery: automatic test, build and deploy on every change.
IaC (Bicep, Terraform, CDK)
Infrastructure as code: describing cloud resources in files so they are repeatable and reviewable.
ACR / ECR
Azure Container Registry / Amazon Elastic Container Registry: where container images are stored.
pgvector
A Postgres extension that adds vector search.
Private endpoint / VNet / VPC
Private network connections so databases and AI services are not exposed to the internet.
CDN / WAF
Content delivery network (caches content near users) / web application firewall (blocks attacks).
Cold start
Delay on the first request when a scaled-to-zero service has to start up.
Provisioned throughput
Reserved LLM capacity for predictable latency at a fixed price.
azd
Azure Developer CLI; 'azd up' provisions and deploys an app from a template.
