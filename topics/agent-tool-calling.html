How an AI agent calls a tool, end to end

Track: Agentic systems.
The key idea: the model never runs anything. It only writes a structured request saying which tool it wants and with what inputs. Your code decides whether to run it.

What it is and the problem it solves

A language model on its own can only produce text from what it learned in training. It cannot check today's order status, query your database, or issue a refund. Tool calling (also called function calling) lets you describe tools to the model: a name, a plain-English description, and the inputs it needs as a JSON schema. When the model decides a tool would help, it replies with a tool call instead of an answer. Your application runs the real function, sends the result back, and the model uses it to write the final answer or to call another tool. An agent is this loop running until the task is done.

How it works

  1. 1. App sends the question plus the tool menuThe user's message, the conversation so far, and a list of tools: name, description, input schema.
  2. 2. Model returns a tool call, not an answerStructured output like: tool = get_order_status, arguments = { order_id: 812 }.
  3. 3. Your code validates and runs itCheck the user is allowed, the arguments are valid, then call the real API or database.
  4. 4. Result goes back to the modelThe tool output is added to the conversation as a tool result message.
  5. 5. Model answers or calls againIt may chain tools (look up order, then check refund). The loop stops at a final answer, a step limit, or a human approval step.
Everyday comparison: a restaurant waiter and the kitchen.
The model is the waiter: it understands what you want and writes the order slip (tool call) in the kitchen's exact format. It does not cook. The kitchen (your code) checks the slip, cooks (runs the function), and hands back the dish (result). The waiter then serves it with a sentence. The menu is the tool list: if a dish is not on it, the waiter cannot order it.

When to use it, when not to

Benefits

  • The model can work with live, private data and take real actions.
  • One assistant can cover many tasks by adding tools rather than retraining.
  • Tools are normal code, so you keep control: validation, permissions, logging.

Trade-offs and risks

  • Every tool round trip adds a model call: more latency and cost.
  • The model can pick the wrong tool or invent arguments; validate everything.
  • Prompt injection: text inside a tool result can try to steer the model. Treat tool output as untrusted.
  • Too many tools in the menu confuses the model and costs tokens on every call.

Pattern card: tool-calling agent loop

What it is
An LLM that requests named functions in a structured format, and an app loop that runs them and feeds results back.
Metaphor
Waiter writes the order slip; the kitchen cooks.
Real example
Klarna's OpenAI-powered assistant handles refunds, returns, payment issues and balances for customers.
Use when
The answer depends on live systems, or the user wants something done, and the steps vary per request.
Do not use when
The steps are fixed (use a normal workflow) or the answer is in documents only (use RAG).
Trade-offs
Flexibility in exchange for extra latency, cost and the need for guardrails.
Instruction to give AI or a teammate
Build a tool-calling loop with three tools (get_order, get_refund_status, request_refund), validate arguments against the schema, require human approval for request_refund, cap the loop at 5 steps, and log every tool call.

Real company: Klarna

Klarna announced on 27 Feb 2024 that its AI assistant, powered by OpenAI, handled 2.3 million conversations in its first month, two-thirds of its customer service chats, covering refunds, returns, payment issues, cancellations, disputes and real-time balance and payment-schedule updates. Klarna's CEO told Inc. the assistant does not have authority to approve refunds on its own. Klarna has not published its internal design; answering "what is my balance" for a specific customer requires the assistant to read live account data, which is exactly what tool calling provides, and the refund limit is a human-in-the-loop guardrail.

Why it matters on the job: an FDE's real work in an agent project is mostly the tools: which systems to expose, with what permissions, which actions need approval, and how to log and evaluate the calls. The model is the easy part.

Where it shows up in code you'll read

tap to expand

Look for three things: a list of tool definitions, a loop, and a branch that checks whether the model returned a tool call.

# Python (OpenAI / Azure OpenAI style), shape only
tools = [{"name": "get_order_status", "description": "...", "parameters": {...}}]
while True:
    reply = llm(messages, tools=tools)
    if not reply.tool_calls: break            # final answer
    for call in reply.tool_calls:
        result = run_tool(call.name, call.arguments)   # YOUR code runs it
        messages.append(tool_result(call.id, result))
// TypeScript / Next.js: Vercel AI SDK defines tools as objects with a description,
// an input schema (zod) and an execute() function, plus a max-steps limit.
// Java: Spring AI and LangChain4j mark a normal method as a tool with an annotation
// (@Tool); the framework builds the schema and runs the loop for you.

Where Azure fits: Azure OpenAI supports the same function calling, and Azure AI Foundry Agent Service runs the loop for you with built-in tools. AWS equivalent: Amazon Bedrock Converse API tool use and Bedrock Agents. GCP: Vertex AI Gemini function calling. More on this in the MCP drop.

Interview angle

  • "How does an LLM call an API?" Strong answer: it doesn't; it emits a structured call against a schema you gave it, your runtime executes it with its own credentials and checks, and the result is fed back. Mention the loop, step limits, and validation.
  • "How do you make a tool-using agent safe in production?" Strong answer: least-privilege credentials per tool, argument validation, human approval for irreversible actions, treat tool output as untrusted (prompt injection), timeouts and retries, and logging every call for evaluation and audit.

Glossary

LLM
Large language model, e.g. GPT, Claude, Gemini, Grok.
Tool / function calling
The model replies with a structured request to run a named function instead of plain text.
Tool definition
Name + description + input schema that tells the model what a tool does and needs.
JSON schema
A standard way to describe the shape of data: fields, types, which are required.
Arguments
The input values the model fills in for a tool call.
Agent / agent loop
Code that repeatedly calls the model, runs requested tools, and feeds results back until done.
Human-in-the-loop (HITL)
A person approves certain actions before they happen.
Prompt injection
Malicious text (in a web page, email or tool result) that tries to make the model ignore its instructions.
Tokens
The chunks of text a model reads and writes; cost and limits are measured in them.
RAG
Retrieval-augmented generation: fetch relevant documents and give them to the model.
zod
A TypeScript library for describing and validating data shapes.
Annotation (@Tool)
A Java label on a method that tells a framework to treat it specially.
MCP
Model Context Protocol: a standard way to plug tools into any AI app.
