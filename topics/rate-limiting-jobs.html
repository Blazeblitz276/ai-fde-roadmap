Rate limiting and background jobs: token bucket, backpressure, retries, dead-letter queues

Track: System design fundamentals. This topic is how to use queues and limiters to protect a system.
Every system has a speed limit: a database, a GPU, an LLM API with tokens-per-minute quota. Rate limiting decides who gets in and how fast; background jobs move slow work off the user's request; backpressure, retries and dead-letter queues decide what happens when things still go wrong.

What it is and the problem it solves

Picture a document-AI app: users upload PDFs, your backend runs OCR (a vision model), embeds the text and calls an LLM to summarise. One customer runs a script that uploads 5,000 files in a minute. Without protection, three things break: your API servers run out of workers so normal users time out, your LLM provider returns 429 Too Many Requests because you blew your tokens-per-minute quota, and failed requests get retried immediately which makes the overload worse (a retry storm).

Four tools fix this, and they work together:

How it works

  1. 1. Token bucket at the doorEach tenant has a bucket that holds up to 50 tokens and refills at 10 per second. Each request takes one token. Bursts up to 50 pass; sustained traffic above 10/s gets 429 with a Retry-After header. The bucket state usually lives in Redis so every API server sees the same count.
  2. 2. Accept, don't doThe API stores the file, puts a small message ({job_id, file_url}) on the queue and immediately returns 202 Accepted with the job ID. The user's request is fast no matter how slow the AI work is.
  3. 3. Workers pull at a safe paceWorkers pull jobs only when they have capacity (a concurrency cap sized to the LLM quota). If the queue grows, the system slows gracefully instead of crashing; autoscaling can add workers based on queue depth.
  4. 4. Retry with backoffIf the LLM returns 429 or times out, the worker does not acknowledge the message. It reappears after a visibility timeout and is retried, ideally with growing delays. Workers must be idempotent: running a job twice gives the same result.
  5. 5. Dead-letter the hopelessAfter N failed attempts (e.g. 5) the broker moves the message to a DLQ. A corrupt PDF stops blocking the line; you alert on DLQ size, inspect, fix, and 'redrive' the messages back.
Everyday comparison: a popular restaurant.
The host at the door seats a few parties a minute and gives the rest a buzzer (rate limiter + Retry-After). Orders go onto the ticket rail (job queue), and cooks take tickets only when they have a free burner (workers with a concurrency cap). If the rail is overflowing, the host stops taking walk-ins (backpressure). A dish sent back is remade a couple of times (retry), but a dish that keeps failing goes to the manager's table for a look (dead-letter queue) so it does not hold up every other order.

When to use / when not to use

Solid arrows = yes, dashed = no. Rule of thumb: every public or multi-tenant API gets a rate limiter; anything slow, bursty or quota-bound becomes a background job.

Benefits

  • One noisy tenant cannot take down everyone else (fairness).
  • Bursts become a longer queue, not an outage.
  • Failures are retried automatically; poison messages are parked, not lost.
  • You can size workers to your LLM quota and budget.

Trade-offs

  • Async UX: the user gets 'processing...' and you need status polling, webhooks or push.
  • Retries mean duplicates: every worker must be idempotent.
  • More moving parts to monitor (queue depth, age of oldest message, DLQ size).
  • Limits set too low frustrate good customers; too high and they protect nothing.

Pattern card: Queue-based load leveling + token bucket

What it is
Limit each caller with a token bucket at the edge, and push slow work onto a queue that workers drain at a safe, capped pace, with retries and a dead-letter queue.
Metaphor
Restaurant host with buzzers, a ticket rail, and a manager's table for problem dishes.
Real example
Stripe's four rate limiters (below); Microsoft documents it as the 'Queue-Based Load Leveling' cloud design pattern.
Use when
Multi-tenant APIs, bursty uploads, anything calling an LLM, GPU or third-party API with a quota.
Do not use when
A tiny internal tool with a handful of users, or real-time interactions that cannot wait (use capacity, not queues).
Trade-offs
Stability and fairness in exchange for async UX, idempotency work and more monitoring.
Instruction to give AI or a teammate
Add a Redis token-bucket limiter per tenant (10 req/s, burst 50, return 429 with Retry-After); make /upload return 202 with a job ID and enqueue the work on Azure Service Bus; run workers with max 8 concurrent LLM calls, idempotent by job ID, 5 deliveries then dead-letter; alert when the DLQ is non-empty or the oldest message is older than 10 minutes.

Real company: Stripe

Stripe's engineering post 'Scaling your API with rate limiters' describes four limiters they run in production. The most important is a request rate limiter (N requests per second per user, with short bursts allowed), implemented as a token bucket in Redis; it rejects millions of requests a month, often from test scripts that got out of hand. A concurrent-requests limiter caps how many requests a user has in flight. Two load shedders protect the whole fleet: one reserves a share of capacity for critical calls such as creating charges, and one sheds traffic in priority order (test mode first, then GETs, then POSTs, critical methods last) when workers are overloaded, ramping slowly to avoid oscillation.

Why it matters on the job: as an FDE you will put a customer's AI app in front of a real LLM quota. The first production incident is very often a 429 storm or one tenant starving the others. Knowing 'token bucket at the edge, queue in the middle, DLQ at the end' lets you design it in on day one.

Where it shows up in code you'll read

# Python (FastAPI + a queue), conceptually
if not limiter.allow(tenant_id):                 # token bucket in Redis
    raise HTTPException(429, headers={"Retry-After": "2"})
job_id = save_upload(file)
queue.send({"job_id": job_id})                   # SQS / Service Bus / Celery
return {"job_id": job_id, "status": "queued"}, 202

# worker
for msg in queue.receive(max_messages=8):          # concurrency cap
    if already_done(msg.job_id): msg.complete(); continue   # idempotent
    process(msg)                                     # exception => message comes back, then DLQ
    msg.complete()
// TypeScript / Next.js: middleware.ts with @upstash/ratelimit (sliding window or token bucket);

// Java / Spring: Bucket4j or Resilience4j RateLimiter on a controller; @SqsListener or

Interview angle

  • 'Design rate limiting for a multi-tenant LLM API.' Strong answer: limit on both requests and tokens per tenant (LLM cost is per token), token bucket in a shared store like Redis or at the gateway (APIM llm-token-limit / API Gateway usage plans), return 429 + Retry-After, separate tiers per plan, a concurrency cap on the model calls, queue long jobs, and monitor rejections per tenant.
  • 'A job keeps failing and blocks the queue. What do you do?' Strong answer: bounded retries with exponential backoff and jitter, idempotent workers, dead-letter after N attempts, alert on DLQ, root-cause, fix, redrive; distinguish transient errors (retry) from permanent ones (fail fast to DLQ).

Glossary

Rate limiting
Capping how many requests a caller may make in a time period.
Token bucket
Algorithm: a bucket of tokens refills steadily; each request spends one; empty bucket = reject. Allows short bursts.
Burst
A short spike above the steady rate.
429 Too Many Requests
HTTP status meaning 'you are being rate limited'.
Retry-After
Response header telling the client how long to wait before trying again.
202 Accepted
HTTP status meaning 'received, will process later'.
Background job / worker
Work done outside the user's request by a separate process that pulls from a queue.
Backpressure
A signal that pushes back on producers to slow down when consumers are full.
Load shedding
Deliberately dropping low-priority requests during overload to save critical ones.
Visibility timeout
Time a pulled message is hidden from other workers; if not acknowledged, it reappears.
Acknowledge (ack / complete)
Telling the broker the message is done so it is deleted.
Idempotent
Doing it twice has the same effect as doing it once.
Dead-letter queue (DLQ)
A side queue for messages that failed too many times.
Poison message
A message that will always fail (e.g. corrupt file).
Redrive
Moving messages from the DLQ back to the main queue after a fix.
maxReceiveCount / MaxDeliveryCount
SQS / Azure Service Bus setting: attempts before dead-lettering.
Tokens per minute (TPM)
LLM provider quota on how many tokens you can process per minute.
Retry storm
Many clients retrying at once, multiplying the load that caused the failure.
