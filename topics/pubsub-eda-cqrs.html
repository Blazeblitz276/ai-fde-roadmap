Architecture patterns part 3: pub/sub, event-driven architecture, CQRS

Track: SE and architecture patterns. Builds on drop 2 (message queues) and drop 4 (saga).
Three related ideas. Pub/sub is the mechanism (one message, many listeners). Event-driven architecture is the style of building a whole system around 'something happened' messages. CQRS is a data pattern: use one model for changing data and a different model for reading it, often kept in sync by events.

What it is and the problem it solves

PatternProblemOne-line idea
Pub/subThe order service has to call email, analytics, loyalty, fraud... and changes every time a new team wants the dataThe publisher posts a message to a topic; any number of subscribers receive their own copy; the publisher does not know who they are
Event-driven architecture (EDA)Services calling each other in long synchronous chains are tightly coupled and fail togetherServices announce facts ('OrderPlaced') and others react in their own time
CQRSOne database model is awkward for both heavy writes with rules and fast, varied reads (dashboards, search, feeds)Split the command (write) side from the query (read) side, each with its own model and possibly its own database

Queue vs pub/sub (from drop 2): in a queue, each message is processed by one worker (work sharing). In pub/sub, each subscriber group gets every message (broadcast). Kafka, Azure Service Bus topics, AWS SNS (+ SQS), EventBridge and GCP Pub/Sub all do pub/sub.

How they work

Pub/sub and event-driven: one event, many independent reactions.

CQRS: writes go through rules into the write store; events update read models shaped for each screen.

CQRS often travels with event sourcing: instead of storing only the current value, you store every change as an event (like a bank statement) and rebuild current state, or any read model, by replaying them. You can use CQRS without event sourcing.

Everyday comparisons.
Pub/sub is a WhatsApp broadcast or a YouTube channel: you post once, every subscriber gets it, and you do not track who they are. Event-driven is a newsroom: reporters file stories when things happen and each desk (sports, business, web) reacts on its own. CQRS is a restaurant: the kitchen (write side) follows strict recipes and hygiene rules; the menu board and the takeaway display (read side) are separate copies shaped for customers, updated whenever the kitchen changes something.

When to use / when not to use

Solid arrows = yes, dashed = no.

Benefits

  • Add new consumers without touching the producer (loose coupling).
  • Absorbs spikes; one slow consumer does not slow the others.
  • CQRS lets reads and writes scale and evolve independently; event sourcing gives a full audit trail.

Trade-offs

  • Eventual consistency: the read side may lag by milliseconds to seconds.
  • Harder to debug: no single call stack; you need correlation IDs and tracing (drop 4).
  • Duplicates and out-of-order events: consumers must be idempotent (drop 3). CQRS + event sourcing is heavy; overkill for simple CRUD apps.

Pattern cards

Pub/sub: what
Publishers send messages to a topic; every subscriber gets a copy; neither knows about the other.
Pub/sub: metaphor + example
YouTube channel. LinkedIn built Kafka in 2010 as a publish-subscribe system for its activity and event data, open-sourced it in 2011, and by 2019 reported running over 7 trillion messages a day through it.
Pub/sub: use / avoid
Use for fan-out notifications, activity streams, feeding analytics. Avoid when you need a reply right away or exactly one handler (use a queue or an API).
Pub/sub: instruction
Publish an OrderPlaced event to an Azure Service Bus topic with subscriptions for email, fraud and analytics, include an event ID and correlation ID, and make each subscriber idempotent with a dead-letter queue after 5 failed attempts.
EDA: what
A system style where services communicate mainly by emitting and reacting to events (facts in past tense).
EDA: use / avoid
Use when many teams and services react to business moments (order placed, image uploaded, payment failed). Avoid for small apps with one team, or flows that must be strictly step-by-step and immediate.
EDA: instruction
When an image lands in the uploads bucket, emit an ImageUploaded event via EventBridge, let the defect-detection worker and the thumbnail worker subscribe separately, and publish DefectDetected for the alerting service; document every event schema in a registry.
CQRS: what
Separate models (and often stores) for commands that change state and queries that read it.
CQRS: metaphor + example
Restaurant kitchen vs menu board. Grab's Fare Storage stores every fare change as an event in DynamoDB (event sourcing) and uses CQRS so different services read fares their own way; Grab reported faster debugging from the audit trail and independent scaling of fare and booking data.
CQRS: use / avoid
Use when reads vastly outnumber writes or need different shapes, or you need history/audit. Avoid for simple CRUD, or when users must always see their own write instantly and you cannot design around it.
CQRS: instruction
Split the claims service into a command API that validates and writes to PostgreSQL and emits ClaimUpdated events, and a read model in Cosmos DB shaped for the agent dashboard, updated by a consumer; show users a 'processing' state until the read model catches up.

Real-world scenario and why it matters on the job

LinkedIn: Kafka was created there to move activity data (page views, searches, profile updates) to many consumers at once (feeds, analytics, monitoring, search indexing) without each producer knowing about each consumer. That decoupling is why Kafka became the default event backbone at many companies. Grab (2020 engineering blog): their legacy store kept only the latest fare, so debugging fare disputes was slow; they moved to an event-sourced Fare LifeCycle service on DynamoDB with CQRS, streaming updated events to a message queue for receipts and archiving.

On the job: customer architectures you inherit will be full of topics, events and read models. Being able to say 'this needs a topic, not a direct call' or 'CQRS is overkill here' is exactly the lead-level judgment an FDE is hired for. AI tie-in: LLM jobs (summarise a ticket, classify a document) are naturally event-driven: TicketCreated triggers the AI worker, which emits TicketSummarised.

@bus.subscribe("orders", group="email")          # each group gets every event

    if seen(evt["id"]): return                   # idempotent

# CQRS
def place_order(cmd): validate(cmd); write_db.save(order); bus.publish(...)   # command side
def order_summary(user_id): return read_db.get("order_summaries", user_id)    # query side

// TypeScript / Next.js: a route handler publishes to Service Bus / SNS / Pub/Sub with the cloud SDK;

// Clues you are looking at CQRS: folders named commands/ and queries/, two DB connections, 'projection' or 'read model'.

FDE / architect interview angle

  • 'Queue or pub/sub?' Strong answer: queue when one worker should do each job (work distribution, rate limiting); pub/sub when many independent consumers need the same fact. Often both: SNS topic fanning out to an SQS queue per consumer.
  • 'What breaks in event-driven systems and how do you handle it?' Strong answer: duplicates (idempotency keys), ordering (partition by entity ID), poison messages (DLQ), schema changes (versioned schemas, registry), lost visibility (correlation IDs, tracing), and the dual-write problem (outbox pattern).

Glossary

Topic
A named channel that publishers send to and subscribers listen on.
Publisher / subscriber
The sender of messages / a receiver that registered interest in a topic.
Consumer group
A set of workers sharing one subscription; each event goes to one worker in the group, and every group gets every event.
Event
A message stating a fact that already happened, named in past tense (OrderPlaced).
Fan-out
One message delivered to many receivers.
Loose coupling
Parts of a system can change or fail without forcing changes in the others.
Synchronous / asynchronous
Caller waits for the answer / caller continues and the work happens later.
CRUD
Create, Read, Update, Delete: the basic one-model-one-database approach.
Command / query
A request that changes state / a request that only reads.
Read model / projection
A copy of data reshaped for a specific screen or query, built from events.
Event sourcing
Storing every change as an event and deriving current state by replaying them.
Event store
The database that holds the event history.
Eventual consistency
Copies of data agree after a short delay, not instantly.
Idempotent
Processing the same message twice has the same effect as once (drop 3).
Partition (Kafka)
A slice of a topic; events with the same key stay in order within one partition.
Schema registry
A central place that stores and versions the format of each event.
Outbox pattern
Write the event into the same database transaction as the data change, then publish it from there, so you never update one without the other.
DLQ
Dead-letter queue: where messages go after repeated failures (drop 3).
