Message queues by use case: Kafka vs RabbitMQ vs SQS / Service Bus vs Redis Streams

What it is and the problem it solves

Without a queue, service A calls service B directly and waits. If B is slow, A is slow; if B is down, A fails; if traffic spikes 10x, B falls over. A message broker sits in between: A (the producer) drops a message and moves on; B (the consumer) picks it up when ready. This decouples the two in time and load, absorbs spikes (the queue just gets longer), and lets you retry failed work.

There are two families. Message queues (RabbitMQ, Amazon SQS, Azure Service Bus queues, Azure Storage Queues) deliver each message to one consumer, who acknowledges it, and then it is gone: ideal for jobs and tasks. Event streams / logs (Apache Kafka, Amazon Kinesis, Azure Event Hubs, Redis Streams; GCP Pub/Sub sits in between) append events to an ordered, retained log; many independent consumer groups each read at their own position and can replay history: ideal for activity tracking, analytics and event-driven systems.

How it works

Everyday comparison: a restaurant ticket rail vs a newspaper.
A queue is the kitchen ticket rail: each order slip is grabbed by one cook, cooked once, and thrown away. A stream is a newspaper archive: every edition is kept; the sports desk, the finance desk and a researcher next year can each read the same edition independently, from wherever they left off.

Benefits of putting a broker in between

  • Spikes are absorbed: the queue grows instead of the service crashing.
  • Services deploy, scale and fail independently.
  • Failed work can be retried or parked in a dead-letter queue instead of lost.

Trade-offs

  • Asynchronous: the user doesn't get the result instantly; you need status checks or notifications.
  • Messages can arrive twice or out of order, so consumers must be idempotent (safe to repeat).
  • One more system to monitor (queue depth, consumer lag).

Pattern card: queue-based load levelling

What it is
Put a queue between a fast producer and a slower worker so bursts are buffered and processed at a steady rate.
Metaphor
Kitchen ticket rail: orders pile up on the rail at lunch rush; cooks work through them steadily.
Real example
LinkedIn built Kafka for activity events (below); SQS / Service Bus queues are the default for background jobs on AWS / Azure.
Use when
Work is slow (LLM calls, video/CV processing, emails), traffic is bursty, or you call a rate-limited API.
Do not use when
The user must see the result in the same request in under a second, or the system is tiny and a direct call is fine.
Trade-offs
Resilience and smooth load in exchange for async UX, duplicates to handle, and monitoring.
Instruction to give AI or a teammate
Move document processing off the request path: the API puts a job on an Azure Service Bus queue and returns a job ID, a worker in Container Apps processes it idempotently with 5 retries then dead-letters it, and the UI polls job status.

Real company: LinkedIn and Kafka

Kafka was built at LinkedIn around 2010 (by Jay Kreps, Neha Narkhede and Jun Rao) to move huge volumes of activity events (page views, searches, ads shown) into both real-time systems and Hadoop/the data warehouse, then open-sourced. LinkedIn's engineering blog reports more than 100 Kafka clusters, 4,000+ brokers, 100,000+ topics and over 7 trillion messages a day, powering activity tracking, message exchange and metrics. That is the archetypal stream use case: one event, many readers, replayable.

Why it matters on the job: AI workloads are slow and bursty (LLM calls, CV inference on uploaded images). An FDE who puts a queue in front of the model, with retries and a dead-letter queue, turns a demo that times out under load into something production-ready.

Interview angle

  • "Kafka or SQS for X?" Strong answer: ask whether many consumers need the same events or replay (Kafka/Event Hubs) vs one-off jobs (SQS/Service Bus); weigh ops cost; mention ordering, retention and managed options.
  • "How do you handle a message that keeps failing?" Strong answer: limited retries with backoff, then a dead-letter queue with alerting, idempotent consumers so retries are safe, and a way to replay fixed messages.

Glossary

Message broker
Middleware that receives messages from producers and delivers them to consumers.
Producer / consumer
Sender of messages / reader or worker that processes them.
Queue vs stream (log)
Queue: each message to one consumer, then deleted. Stream: ordered, retained events read by many.
Topic / partition
A named stream / a slice of it that allows parallel reading and ordering within the slice.
Consumer group
A set of workers sharing one reading position on a stream.
Retention / replay
How long events are kept / re-reading old events.
Acknowledgement (ack)
The consumer telling the broker 'done, delete it'.
Dead-letter queue (DLQ)
Where messages go after too many failed attempts, for inspection.
Idempotent
Safe to run twice with the same result (e.g. 'set status = paid', not 'add 100').
FIFO
First in, first out: strict ordering.
Consumer lag / queue depth
How far behind consumers are / how many messages are waiting.
Change data capture (CDC)
Streaming every database change as an event.
Load levelling
Buffering bursts so downstream work runs at a steady pace.
