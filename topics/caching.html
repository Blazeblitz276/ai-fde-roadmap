Caching in a real system

Track: System design fundamentals.
A cache is a small, fast copy of data that is expensive to fetch. The design questions are: who fills it, when does it go stale, and what gets thrown out when it is full.

What it is and the problem it solves

Databases and external APIs are slow and costly compared with memory. Most apps read the same data far more often than they change it (a product page, a user profile, an LLM answer to a common question). A cache, usually Redis or Memcached, keeps recent results in memory so most reads never reach the database. This cuts latency from tens of milliseconds to around one, and protects the database from load it could not handle.

Everyday comparison: your fridge and the supermarket.
The supermarket is the database: has everything, but a trip takes time. The fridge is the cache: small, right there. You check the fridge first (cache hit), go to the shop only when it is empty (miss) and restock on the way back (cache-aside). Milk has an expiry date (TTL). When the fridge is full you throw out what you haven't touched in longest (LRU). If the recipe changes, you bin the old ingredients (invalidation).

When to use it, when not to

Benefits

  • Much lower latency for repeat reads.
  • Database handles a fraction of the traffic, so it is cheaper and safer.
  • Can shield slow or rate-limited external APIs (including LLM APIs).

Trade-offs

  • Stale data: the cache can disagree with the database for a while.
  • Another system to run, monitor and pay for.
  • Thundering herd: a popular key expires and thousands of requests hit the DB at once.
  • Bugs in invalidation are notoriously hard to find.

Pattern card: cache-aside

What it is
The app checks the cache first, loads from the database on a miss and fills the cache; on writes it updates the database and deletes the cached key.
Metaphor
Check the fridge, shop only when empty, restock on the way back.
Real example
Facebook runs memcache as a demand-filled look-aside cache in front of MySQL, serving billions of requests per second.
Use when
Read-heavy data where a few seconds of staleness is acceptable.
Do not use when
Data must be exact at every moment, or it is written as often as it is read.
Trade-offs
Big speed and DB savings in exchange for possible stale reads and invalidation work.
Instruction to give AI or a teammate
Add cache-aside with Redis for the product and profile reads: key by entity id, 10-minute TTL, delete the key after every DB write, LRU eviction, and log the hit rate.

Real company: Facebook (Meta)

Facebook's NSDI 2013 paper "Scaling Memcache at Facebook" describes memcache as a "demand-filled look-aside cache": on a miss the web server reads the database and fills the cache; on a write it updates the database and then deletes the cached key. They delete rather than update because deletes are idempotent (safe to repeat). They also describe the stale-data race this creates and the "leases" they added to fix it, and the thundering-herd problem. Meta's engineering blog says Facebook started using memcached in 2005 when page loads were slowing down.

Why it matters on the job: almost every customer system you touch has a cache somewhere, and "why is the dashboard showing old data?" is a classic production ticket. Knowing the pattern tells you where to look: TTL, missing invalidation, or a race.

Where it shows up in code you'll read

# Python - cache-aside in three lines
user = redis.get(f"user:{id}")
if user is None:
    user = db.load_user(id); redis.set(f"user:{id}", user, ex=600)  # TTL 600 s
# on update: db.save(user); redis.delete(f"user:{id}")
// Java (Spring Boot): @Cacheable("users") on a method = cache-aside;
// @CacheEvict on the update method = delete-on-write. Redis configured as the cache store.

// Next.js: fetch(url, { next: { revalidate: 600 } }) caches a response with a TTL;
// revalidateTag()/revalidatePath() after a write is invalidation.

Managed Redis on each cloud: AWS ElastiCache (Redis/Valkey), Azure Cache for Redis (Azure Managed Redis), GCP Memorystore. Caching inside LLM and RAG apps (semantic and prompt caching) has its own topic: Caching in LLM and RAG apps.

Interview angle

  • "Design caching for a product catalogue." Strong answer: cache-aside in Redis, key design, TTL chosen by how fresh each field must be, delete-on-write, eviction policy, measuring hit rate, and protecting against a thundering herd (staggered TTLs or a lock so only one request refills).
  • "What can go wrong with caching?" Strong answer: stale reads, invalidation races, cache stampede, cold starts after a restart, and the cache quietly becoming a dependency the system can't run without, with Facebook's paper as a real reference.

Glossary

Cache hit / miss
Hit: the data was in the cache. Miss: it wasn't, so you go to the source.
Hit rate
Share of reads served from the cache; the main health number for a cache.
Redis / Memcached
Popular in-memory key-value stores used as caches.
Key-value store
Storage where you save and fetch a value by a unique key, like user:42.
Cache-aside / look-aside
The app manages the cache itself: check, load on miss, fill.
Write-through
Every write goes to cache and DB at the same time.
Write-behind
Write to cache now, to the DB later in batches.
TTL
Time to live: how long an entry stays before it expires.
Eviction, LRU, LFU
Removing entries when full; least recently used; least frequently used.
Invalidation
Removing or updating cached data when the original changes.
Stale data
A cached copy that no longer matches the source.
Idempotent
Doing it twice has the same effect as once (deleting a key).
Thundering herd / cache stampede
Many requests miss at once and overload the database.
Lease
Facebook's token that stops an old value being written into the cache after a newer delete.
NSDI
A top academic conference on networked systems.
