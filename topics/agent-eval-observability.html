Agent evaluation and observability

Track: Agentic systems + Production & ops. Builds on drop 1 (tool calling), drop 3 (RAG evals), drop 4 (logs, metrics, traces) and drop 6 (multi-agent, guardrails).
A normal API either works or throws an error. An agent can return HTTP 200 and still pick the wrong tool, loop ten times, leak data or confidently answer the wrong question. Agent observability lets you see every step it took; agent evaluation tells you whether those steps and the final outcome were good, before and after you ship.

What it is and the problem it solves

PieceQuestion it answersTypical signal
Tracing (observability)What exactly did the agent do, step by step?A trace tree: user request -> agent turn -> model call -> tool call -> sub-agent, with inputs, outputs, tokens, cost, latency per step
Offline evaluationIs version B better than version A before we deploy?Scores on a fixed golden dataset run in CI
Online evaluationIs it still good on real traffic right now?Sampled production traces graded automatically, user feedback, business KPIs
Dashboards and alertsIs something drifting or breaking?Task success rate, tool error rate, steps per task, cost per task, p95 latency, guardrail hits

What you grade in an agent is wider than in RAG (drop 3): the final answer (correct, grounded), the trajectory (right tools, right order, no pointless loops), the tool calls themselves (valid arguments, success rate), safety (refusals, prompt-injection robustness, data leaks) and efficiency (steps, tokens, cost, time).

How it works

  1. Instrument with OpenTelemetryOpenTelemetry (drop 4) has GenAI semantic conventions: standard span names and fields for agent invocations (invoke_agent), model calls and tool executions (execute_tool). They are still marked 'Development' status, but Microsoft Foundry tracing and Amazon Bedrock AgentCore Observability both build on them, so one instrumentation can feed several back ends.
  2. Pick where traces landAzure: Foundry tracing exported to Azure Monitor Application Insights. AWS: AgentCore Observability on CloudWatch. GCP: Cloud Trace. Vendor-neutral: LangSmith, Langfuse, Arize Phoenix and similar. Self-host if data cannot leave your perimeter.
  3. Build the offline eval setStart with 30-100 realistic tasks with expected outcomes (which tools, what final state). Grade with code first (did it call refund_order once, with the right id?), then an LLM judge calibrated against human labels for fuzzy qualities (drop 3).
  4. Gate deploysRun the suite in CI on every prompt, model or tool change; block the release if critical scenarios fail or scores drop.
  5. Close the loop onlineSample production traces, auto-grade them, collect thumbs up/down and escalations, alert on drift, and promote failing traces into the golden set. This loop is the heart of LLMOps.
Everyday comparison: a flight's black box plus the pilot's simulator check.
Tracing is the flight data recorder: after any incident you can replay every control input and instrument reading. Evaluation is the simulator check pilots must pass regularly against a fixed set of emergencies (offline), plus the airline watching real flight data for unsafe patterns (online). A dangerous real event becomes a new simulator scenario, just as a bad production trace becomes a new test case.

When to use / when not to use

SituationWhat you need
Prototype or demo, single prompt, no toolsBasic logging and 10-20 hand-checked examples; full LLMOps is overkill
Agent that calls tools or touches customer dataFull tracing from day one, plus a code-graded offline suite
Multi-agent or long-running workflowsTrace trees with sub-agent spans, trajectory evals, step and cost budgets with alerts
Regulated customer (bank, health, government)Self-hosted or in-region traces, PII redaction in spans, audit retention, human review queue
Many teams building agentsA shared platform: standard SDK, one trace back end, an LLMOps maturity checklist
Trade-offDetail
Visibility vs privacyFull prompts and tool outputs in traces help debugging but may store PII; redact or hash fields, restrict access
Coverage vs costTracing everything and LLM-judging every trace costs money; sample online grading (for example 5-10%)
LLM judge vs code checksJudges handle fuzzy quality but drift and are biased; prefer deterministic checks where possible and calibrate judges on human labels
Vendor tool vs cloud nativeSpecialised tools are richer for agents; cloud-native keeps data and billing in one place. OpenTelemetry keeps you portable

Pattern card: trace-everything, eval-gated agent releases

What it is
Every agent run emits an OpenTelemetry trace tree; a versioned eval suite built from real traces gates each release; sampled production traces are graded continuously and failures flow back into the suite.
Metaphor
Black box recorder plus recurring simulator checks for pilots.
Real example
Rippling (pulls failing production traces, re-runs evals, ~10 deploy-blocking scenarios) and Orange Business (3-layer evaluation: RAG quality, agent behaviour, production monitoring), both on LangSmith per LangChain's customer posts.
Use when
Any agent with tools, customer data or more than one step, especially before handing it to a customer.
Do not use when
Throwaway prototypes; there a notebook of examples is enough.
Trade-offs
Slower first release and some tooling cost, in return for catching regressions before customers do and being able to explain any failure.
Instruction to AI / a teammate
Instrument the agent with OpenTelemetry GenAI spans for every model and tool call (redact PII), send them to Application Insights, build a 50-case golden set with code-graded tool checks plus a calibrated LLM judge, and block deploys in CI if critical cases fail or the success rate drops more than 2 points.

Real-world scenarios: Rippling, Orange Business, Schneider Electric

All three are published customer stories on LangChain's blog (vendor-published, so treat numbers as self-reported). Rippling runs a supervisor agent coordinating 5 to 7 specialised sub-agents, shipped in about six months, with layered evals: offline evals with mocks on every commit, 300-400 integration queries against a full sandbox after merge, about 10 deploy-blocking scenarios against real systems, and continuous evals on production several times a day; failing production traces feed a semi-automated loop where an agent proposes fixes and a human reviews the PR. Orange Business grades RAG quality, agent behaviour (tool selection accuracy, task completion, prompt-injection robustness) and production traces (latency, cost, failed runs, human feedback), and requires regression evals before pushing changes. Schneider Electric self-hosts LangSmith on AWS EKS behind its security perimeter, uses one workspace per AI product across dev to prod so production traces can be promoted into test datasets, and tracks 60+ AI products against an internal LLMOps maturity model.

Why it matters on the job
The first thing a customer asks after a pilot is: how do we know it works, and what happens when it does not? An FDE who arrives with a trace view, a golden set and a release gate turns that question into a dashboard instead of a debate, and it is usually what unlocks the move from pilot to production.

with tracer.start_as_current_span('invoke_agent support-bot') as span:
    span.set_attribute('gen_ai.request.model', model_name)
    result = agent.run(user_msg)            # child spans: model calls, execute_tool ...

# offline eval, run in CI
for case in golden_set:
    run = agent.run(case.input)
    assert run.tool_calls == case.expected_tools      # code check
    score = judge(run.answer, case.reference)         # calibrated LLM judge

FDE / architect interview angle

  • Our support agent works in the demo but customers say it sometimes does the wrong thing. How would you fix that? Strong answer: add end-to-end tracing first so failures are visible per step; triage failing traces into categories (retrieval, wrong tool, bad arguments, prompt, model); build a golden set from them; add code checks and a calibrated judge; gate releases; monitor task success, tool error rate and cost per task online.
  • How do you evaluate a multi-step agent, not just its final answer? Strong answer: grade the outcome (task completed, correct final state), the trajectory (right tools, order, no loops), the individual tool calls, safety and efficiency, using deterministic checks where possible and LLM judges only where needed, calibrated on human labels.

Glossary

Observability
Being able to understand what a system did from its outputs (logs, metrics, traces).
Trace / span
A trace is one request's whole journey; a span is one step in it, with start, end and details.
OpenTelemetry (OTel)
The open standard and SDKs for emitting traces, metrics and logs to any back end.
GenAI semantic conventions
OTel's agreed names for AI spans and fields (model, tokens, agent, tool).
OTLP
OpenTelemetry's wire protocol for sending telemetry.
Trajectory
The sequence of steps and tool calls an agent took.
Golden dataset
A curated set of inputs with expected outcomes used for testing.
Offline / online eval
Testing on a fixed set before release / grading live traffic after release.
LLM-as-judge
Using a model to score outputs; must be checked against human labels (calibrated).
Regression
Something that used to work and now fails after a change.
LLMOps
Operating LLM apps in production: tracing, evals, deployment, monitoring, feedback.
Drift
Quality changing over time because inputs, data or models changed.
Supervisor agent / sub-agent
An orchestrating agent that delegates to specialised agents (drop 6).
Sandbox
A safe copy of a system for testing with realistic data.
PII redaction
Removing personal data (names, emails, ids) before storing it.
Application Insights / CloudWatch / Cloud Trace
The Azure / AWS / GCP services that store and visualise telemetry.
AgentCore Observability
AWS's agent tracing and dashboards inside Amazon Bedrock AgentCore.
EKS
Amazon's managed Kubernetes (drop 5).
