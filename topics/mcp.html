MCP: the USB-C port for AI tools (and where Azure fits)

Track: Agentic systems. Prerequisite: drop 1, topic 2 (how an agent calls a tool).
MCP does not change how a model calls a tool. It standardises how tools are packaged and discovered, so any AI app can plug into any tool server without custom glue code.

What it is and the problem it solves

In drop 1 you saw plain tool calling: your app hard-codes a list of tools (name, description, input schema) and the code that runs each one. That works for one app. But a company with 5 AI apps (a chat assistant, an IDE agent, a support bot...) and 20 systems (GitHub, Jira, Postgres, Salesforce...) ends up writing 5 x 20 = 100 custom integrations, each with its own auth, format and bugs. This is the "M x N integration problem".

The Model Context Protocol (MCP), open-sourced by Anthropic in November 2024, fixes this with one standard. A system is wrapped once as an MCP server. Any MCP-capable AI app (an MCP host, which contains an MCP client) can connect to it, ask "what can you do?", and get back a list of tools in a standard format. 5 + 20 = 25 pieces instead of 100. OpenAI, Microsoft, Google and AWS have all since added MCP support to their agent products.

An MCP server can offer three kinds of things: tools (actions the model can call, like create_ticket), resources (read-only data the app can pull in, like a file or a DB schema) and prompts (reusable templates, like "summarise this PR"). It talks over one of two transports: stdio (the server runs as a local process on your machine) or Streamable HTTP (the server is a remote web service, which is what cloud platforms use).

How it works

  1. 1. ConnectThe host's MCP client connects to each configured server (local process or remote URL) and they agree on capabilities (a handshake).
  2. 2. DiscoverThe client asks each server tools/list. Servers return tool names, descriptions and input schemas: the same menu you hand-wrote in drop 1, now generated automatically.
  3. 3. Model decidesThe host passes those tools to the LLM. The LLM returns a normal tool call, exactly like plain tool calling.
  4. 4. Execute through the protocolThe host sends tools/call to the right server. The server runs the real action (with its own auth) and returns the result.
  5. 5. AnswerThe result goes back to the LLM, which answers or calls the next tool. Add a new server and the agent gains new skills with no code change in the host.
Everyday comparison: USB-C.
Before USB-C every phone, camera and laptop had its own charger and cable. Now any device with a USB-C port works with any USB-C accessory. MCP is the port: the AI app is the laptop, each MCP server is an accessory (a keyboard, a drive, a monitor), and the protocol is the shape of the plug plus the rule that devices announce what they are when plugged in (discovery).

When to use it, when not to

You want to use tools other teams or vendors already published (GitHub, Slack, Jira MCP servers)You write wrappers yourselfBest: plug in
Customer wants their internal API usable by Copilot, Claude and their Foundry agentThree integrationsOne MCP server
Ultra-low-latency, single fixed call pathDirect call is fasterExtra network hop and handshake

Benefits

  • Build an integration once, reuse it in every MCP-capable AI app.
  • Tools are discovered at runtime, so adding a capability needs no host code change.
  • Clear security boundary: the server holds the credentials, not the model or the prompt.

Trade-offs and risks

  • Another service to deploy, secure, monitor and version.
  • Untrusted MCP servers are a real risk: a malicious tool description can inject instructions into the model (tool poisoning). Only connect servers you trust, and restrict allowed_tools.
  • Too many tools confuses the model and costs tokens; curate per agent.

Pattern card: MCP server as an integration layer

What it is
Wrap each business system once as an MCP server so any AI app can discover and call its tools through one standard protocol.
Metaphor
USB-C: one port shape, any accessory, devices announce what they are when plugged in.
Real example
Block (Square, Cash App), named by Anthropic as an early MCP adopter (below).
Use when
Several agents or AI tools need the same systems, or you want vendor tools to plug in without custom code.
Do not use when
A single small app with a couple of private functions; plain tool calling is simpler.
Trade-offs
Reuse and governance in exchange for one more service and a new attack surface.
Instruction to give AI or a teammate
Expose our orders API as a remote MCP server over Streamable HTTP with three read tools and one write tool, authenticate with Entra ID, require human approval for the write tool, and register it in our Foundry agent with allowed_tools set.

Real company: Block

When Anthropic launched MCP on 25 Nov 2024, it named Block and Apollo as early adopters; Block's CTO Dhanji Prasanna said they would use it to build agentic systems. Block also built Goose, its open-source AI agent, around MCP. At GraphQL Summit 2025, Block's platform team described how they put thousands of internal APIs (3,000+ services across 700 teams) onto one graph: Goose, grounded with Apollo's MCP server and up-to-date docs, generated the connector schemas, and a multi-agent system they call Flock ran many Goose agents in parallel.

Why it matters on the job: as an FDE, the very common request is "make our internal systems usable by our AI assistant". The architect answer is usually "wrap them as MCP servers with proper auth and approval" rather than hand-wiring each one into each app.

Where it shows up in code you'll read

tap to expand
# Python (official MCP SDK, FastMCP style): a server is just decorated functions
@mcp.tool()
def get_order_status(order_id: int) -> str:
    """Return the status of an order."""   # this docstring becomes the tool description
    ...

# Azure Foundry agent side: register a remote server, not individual functions
McpTool(server_label="orders", server_url="https://orders-mcp.contoso.com/mcp",
        allowed_tools=["get_order_status"])
// TypeScript (official SDK): server.registerTool("get_order_status", { inputSchema }, handler)
// Next.js: an app/api/mcp/route.ts file that serves Streamable HTTP is an MCP server endpoint.
// Java: Spring AI provides MCP server/client starters; tools are annotated bean methods.
// Config you'll see in IDEs: an mcp.json listing servers by name + command or URL.

Interview angle

  • "What is MCP and how is it different from function calling?" Strong answer: function calling is how the model asks for a tool; MCP is how tools are packaged, discovered and invoked across apps. Mention host/client/server, tools/resources/prompts, the M x N problem, and that the model-side loop is unchanged.
  • "A bank wants its agent to use internal APIs via MCP. What worries you?" Strong answer: auth per user (OAuth passthrough vs shared identity), least-privilege allowed_tools, human approval on writes, trusted servers only (tool poisoning), private networking, audit logging, timeouts.

Glossary

MCP (Model Context Protocol)
An open standard for how AI apps discover and use tools and data from separate servers.
MCP host / client / server
Host: the AI app. Client: the connector inside it, one per server. Server: the program exposing tools, resources and prompts.
Tool / resource / prompt
Action the model can call / read-only data the app can load / reusable prompt template.
M x N integration problem
M apps times N systems means M*N custom integrations; a standard turns it into M+N.
Transport (stdio, Streamable HTTP)
How messages travel: through a local process's input/output, or over HTTP to a remote server.
Handshake
The opening exchange where both sides agree on version and capabilities.
Discovery (tools/list)
Asking a server at runtime what tools it offers.
Foundry Agent Service
Azure's managed service for building and running agents (Microsoft Foundry, formerly Azure AI Foundry).
Entra ID / managed identity
Microsoft's identity directory / an identity Azure gives your app so it needs no stored secret.
OAuth identity passthrough
The user signs in and the agent acts with that user's own permissions.
VNet / private endpoint
Your private network in Azure / a way to reach a service without the public internet.
Tool poisoning / prompt injection
Hidden instructions in tool descriptions or data that trick the model into doing something unintended.
Least privilege
Give only the permissions strictly needed.
Goose
Block's open-source AI agent built on MCP.
