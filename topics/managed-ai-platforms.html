Managed AI platforms: Amazon Bedrock vs Microsoft Foundry vs Google Agent Platform

Track: Cloud + AI/LLM systems. Builds on drop 2 (MCP, Foundry Agent Service) and drop 5 (hosting an AI app).
Customers rarely call a model provider directly in production. They go through their cloud's managed AI platform because it brings their existing contracts, identity, network isolation, logging and data-residency promises. Knowing the three platforms side by side is the FDE equivalent of knowing which plug sockets a country uses.

What it is and the problem it solves

A managed AI platform gives you many foundation models behind one API inside your cloud account, plus the building blocks around them: knowledge bases for RAG, agent runtimes, guardrails, evaluation, fine-tuning, and monitoring, all governed by the same IAM, private networking and billing as the rest of your cloud. Names changed a lot recently, so here is the 2026 picture:

How it works: the same shape on every cloud

  1. Pick models from the catalogAccess is granted per account or project; some models are serverless pay-per-token, others need provisioned capacity for guaranteed throughput.
  2. Call through one API with cloud identityNo raw provider API keys in code: the app's managed identity or IAM role is authorised to call the model (drop 1 IAM, drop 7 auth).
  3. Ground itAttach a knowledge base or search index for RAG, and tools for actions.
  4. Wrap with guardrails and evalsContent filters and prompt-injection shields on the way in and out; automated evaluation on a golden set before every change.
  5. OperateQuotas and rate limits per model, token cost dashboards and budgets (drop 3), logs and traces (drop 4).
Everyday comparison: a food court inside your office building.
You could drive to each restaurant (call each model provider directly), but the food court inside your building lets you pay with your staff card (cloud billing and identity), passes the building's hygiene inspection (compliance, guardrails), and you can switch from dosa to noodles without signing a new contract (model choice). Each building (cloud) has its own food court with slightly different stalls.

Trade-offs: the platform's agent and knowledge-base features save weeks but tie you to that cloud; keep your own thin model-calling layer so models can be swapped. Newest models sometimes arrive on a provider's own API before a cloud catalog, and regional availability and quotas differ, so check before promising a customer a model in their region.

Pattern card: model gateway behind one internal interface

What it is
All model calls go through one internal client or gateway that handles auth, retries, logging, cost tags and fallbacks, backed by the cloud's managed platform.
Metaphor
One staff card that works at every stall in the food court.
Real example
DoorDash's Dasher support voice assistant calls Anthropic Claude through Amazon Bedrock with Bedrock Knowledge Bases for RAG (AWS case study).
Use when
Any production LLM app, especially with several models or teams.
Do not use when
A one-day throwaway prototype.
Trade-offs
Small extra layer; in return you get swappable models, central cost and safety control.
Instruction to AI / a teammate
Route every LLM call through one llm_client module that uses the customer's Bedrock (or Foundry) endpoint with the service's IAM role, tags each call with feature and tenant for cost, applies guardrails, retries with backoff, and falls back to a smaller model on throttling.

Real-world scenario and why it matters on the job

DoorDash (AWS case study and AWS Machine Learning blog): Dashers (delivery drivers) prefer to phone support while driving, so latency mattered. Working with the AWS Generative AI Innovation Center for about eight weeks, DoorDash built a voice self-service assistant on Amazon Connect, using Amazon Bedrock to access Anthropic's Claude models and Bedrock Knowledge Bases for retrieval over its help content, with OpenSearch Serverless as the vector store. With Claude 3 Haiku they reached response latency of 2.5 seconds or less. AWS reports the solution fields hundreds of thousands of Dasher calls a day, reduced escalations to live agents by thousands per day, cut generative AI development time by 50 percent, and an automated testing framework raised testing capacity 50x. DoorDash states it does not pass personally identifiable information to these generative AI components.

Why it matters: this is a textbook FDE engagement: a measurable business problem (call volume), a hard non-functional requirement (latency on a phone call), the customer's existing cloud and contact-center stack, a managed platform for model access and RAG, a guardrail and privacy stance, and an evaluation harness that made it safe to roll out. The source is a vendor case study, so in interviews present the numbers as 'reported by AWS'.

FDE / architect interview angle

  • A bank on Azure wants a support copilot; another customer is on AWS. How does your design change? Strong answer: same architecture shape (gateway, RAG, guardrails, evals, observability), different building blocks: Foundry + Azure AI Search + Entra ID + private endpoints vs Bedrock + Knowledge Bases + IAM roles + PrivateLink; keep the app's model layer portable; check model and region availability and quotas.
  • Why not just call the model provider's API? Strong answer: identity and network isolation, data-residency and contract terms the customer already has, one bill, built-in guardrails and logging, and model choice; direct APIs are fine for prototypes or when a needed model is not yet in the catalog.

Glossary

Foundation model
A large pre-trained model (LLM or multimodal) used for many tasks.
Model catalog / Model Garden
The list of models a platform offers.
Serverless (pay-per-token) vs provisioned throughput
Pay per use with shared capacity vs reserved capacity with guaranteed speed.
Token
A chunk of text (roughly three-quarters of a word) that models read and bill by.
Knowledge base
Managed RAG: ingestion, chunking, embeddings and a vector store.
Agent runtime
Managed hosting for agents with sessions, memory and tool access.
AgentCore
AWS's set of managed services for running agents (runtime, memory, gateway, identity).
Guardrails
Filters and policies on inputs and outputs (harmful content, PII, prompt injection).
Evals
Automated tests of model or agent quality on a fixed set of examples.
Quota / throttling
Limit on requests or tokens per minute / being slowed or rejected when you exceed it.
Private endpoint / PrivateLink / VPC Service Controls
Ways to reach cloud services without the public internet / to fence data inside a perimeter.
Data residency
Requirement that data stays in a given country or region.
Lock-in
Cost of switching away from a vendor's specific features.
Amazon Connect
AWS's cloud contact-center (phone and chat) service.
PII
Personally identifiable information.
Fallback model
A cheaper or more available model used when the main one fails or is throttled.
