Architecture patterns part 1: API gateway, circuit breaker, retry with backoff

Track: SE and architecture patterns. These three are the 'front door' and 'seat belts' of any service that calls other services, including LLMs.
In a distributed system something is always slow or down. These patterns decide whether one sick dependency becomes a hiccup or a full outage.

What they are and the problem they solve

Your Next.js frontend calls an orders service, which calls a payment provider and an LLM. Without a front door, every client must know every service's address, and auth, rate limits and logging are re-implemented in each service. And when the payment provider gets slow, the orders service keeps waiting on it, its threads fill up, it stops answering, and the failure spreads backwards to everything that calls it: a cascading failure.

PatternOne lineProtects against
API gatewayOne front door that routes requests to the right service and handles auth, rate limits, TLS and logging in one placeClients coupled to internal services; duplicated cross-cutting code
Retry with exponential backoff + jitterIf a call fails for a temporary reason, wait a bit (longer each time, with randomness) and try again, a limited number of timesBlips: brief network errors, 429s, a restarting pod
Circuit breakerAfter too many failures, stop calling the sick dependency for a while and fail fast or fall back; test with a few calls before resumingLong outages and cascading failures; wasted waiting

How they work together

Circuit breaker states, as a sequence:

Trials succeed: back to CLOSED. Trials fail (dashed): back to OPEN for another wait.

  1. 1. Gateway firstEvery request enters through the gateway, which checks the token, applies the tenant's rate limit (topic 1), and routes /orders to the orders service. Services behind it stay private.
  2. 2. Timeout on every callThe orders service never waits forever: e.g. 2 s for payments. A timeout is the foundation; without it retries and breakers cannot work.
  3. 3. Retry the transientOn a timeout, 429 or 503, retry up to 3 times with exponential backoff (e.g. 200 ms, 400 ms, 800 ms) plus random jitter so thousands of clients do not retry in sync. Never retry a non-idempotent call (like 'charge card') unless it carries an idempotency key.
  4. 4. Breaker stops the bleedingIf most recent calls are failing, the breaker opens: calls fail in microseconds and go to the fallback instead of piling up. Retries sit inside the breaker so an open breaker also stops retry storms.
  5. 5. Recover carefullyAfter the wait, the breaker lets a few trial calls through (half-open). Success closes it; failure reopens it.
Everyday comparisons.
API gateway: the reception desk of an office building: one entrance, ID check, visitor badge, and directions to the right floor. Retry with backoff: redialling a busy phone number, waiting a little longer each time instead of hammering redial. Circuit breaker: the trip switch in your home's electrical panel: when a faulty appliance keeps drawing too much current, the breaker cuts that circuit so the whole house does not catch fire; you reset it once the fault is fixed.

When to use / when not to use

PatternUse whenDo NOT use whenTrade-offs
API gatewaySeveral services or APIs exposed to outside clients; need central auth, rate limits, API keys, versioning, LLM token limitsA single monolith with one frontend (a load balancer is enough); putting business logic in the gatewayCentral control vs an extra hop, a possible bottleneck and single point of failure (run it highly available)
Retry + backoff + jitterTransient failures: network blips, 429, 503, timeouts on idempotent reads or idempotency-keyed writesPermanent errors (400, 401, 404), non-idempotent writes without a key, or when every layer already retries (retries multiply: 3 x 3 x 3 = 27 calls)Higher success rate vs added latency and extra load during incidents
Circuit breakerCalling a remote dependency that can be slow or down for minutes (payment, LLM, legacy system); a fallback existsLocal in-process calls; dependencies with no sensible fallback where failing fast adds nothing; very low traffic (too few calls to judge)Protects the caller and the dependency vs tuning thresholds and handling the 'open' UX

Pattern cards

API gateway: what
A single entry point that routes requests to backend services and centralises auth, rate limiting, TLS, API keys and logging.
Metaphor / example
Office reception desk. Netflix built and open-sourced Zuul as its gateway; managed versions: Azure API Management, AWS API Gateway, GCP API Gateway / Apigee.
Instruction
Put Azure API Management in front of the orders, search and chat services: validate Entra ID JWTs, apply a per-subscription rate limit and an llm-token-limit on the chat route, route by path, and keep the backends on private endpoints.
Retry with backoff + jitter: what
Bounded retries for transient errors, with growing randomised waits, only for idempotent operations.
Metaphor / example
Redialling a busy line, waiting longer each time. AWS SDKs retry with backoff and jitter by default; AWS's Builders' Library documents why.
Instruction
Wrap calls to the LLM and payment APIs with max 3 retries, exponential backoff starting at 200 ms with full jitter, retry only on timeouts, 429 and 5xx, honour Retry-After, send an idempotency key on payment writes, and make sure only this one layer retries.
Circuit breaker: what
A wrapper that tracks failures and, past a threshold, stops calling a dependency for a cooling-off period, failing fast to a fallback, then probes before resuming.
Metaphor / example
The trip switch in your electrical panel. Netflix's Hystrix popularised it (now in maintenance mode; Netflix points new projects to Resilience4j).
Instruction
Add a Resilience4j circuit breaker on the payment client: open at 50% failures over the last 20 calls or when calls exceed 2 s, stay open 30 s, allow 3 half-open trial calls, fall back to queuing the payment as pending, and export breaker state to our dashboards.

Real company: Netflix

Netflix runs hundreds of microservices and published much of the tooling that made these patterns mainstream. Zuul is its edge API gateway; Netflix open-sourced Zuul 2 (asynchronous, built on Netty) in 2018, handling routing, authentication, retries and concurrency protection at the edge. Hystrix, its latency and fault-tolerance library, introduced circuit breakers with fallbacks to stop cascading failures across services. Hystrix's own README now says it is in maintenance mode and that Netflix uses projects like Resilience4j for new internal work, and Spring Cloud replaced Hystrix with Resilience4j and Zuul 1 with Spring Cloud Gateway: a good reminder that the pattern outlives the library.

Why it matters on the job: when you integrate an AI app into a customer's enterprise systems, their legacy APIs WILL be slow at month-end. A lead who says 'timeout, 3 jittered retries, breaker with a pending-state fallback, behind APIM' prevents the 2 a.m. call.

// TypeScript / Node: libraries like opossum (breaker) and p-retry; fetch with AbortSignal.timeout(2000).
// Infra: APIM policies (<retry>, <rate-limit-by-key>), AWS API Gateway routes/usage plans,
//   service meshes (Istio/Linkerd) that add retries and outlier detection without code.

Interview angle

  • 'A downstream service is slow and your service is falling over. What do you do?' Strong answer: timeouts first, bounded retries with jitter only on idempotent calls, a circuit breaker with a fallback, a bulkhead to isolate that dependency's threads (coming in part 2), and monitoring of breaker state; explain cascading failure and retry amplification.
  • 'Why not just retry until it works?' Strong answer: retries multiply load exactly when the dependency is weakest (retry storm), stack across layers, and can double-charge without idempotency keys; cap them, add jitter, retry at one layer, and pair with a breaker.

Glossary

Microservices
An app split into small services that talk over the network.
Dependency (downstream)
A service yours calls; 'upstream' are those calling you.
Cascading failure
One failing service causing its callers, then their callers, to fail.
Cross-cutting concern
Something every service needs: auth, logging, rate limits.
TLS
Encryption for traffic over the network (the 's' in https).
JWT
A signed token that proves who the caller is.
Routing
Deciding which backend gets a request (e.g. by URL path).
Timeout
Maximum time you will wait for a reply before giving up.
Transient error
A temporary failure likely to succeed on retry.
Exponential backoff
Waiting longer after each failure (e.g. doubling).
Jitter
Randomness added to wait times so clients don't retry at the same moment.
Idempotency key
A unique ID sent with a write so a repeated request is applied only once.
Closed / open / half-open
Circuit breaker states: normal / blocking calls / testing recovery.
Fallback
What you do instead when the call can't be made (cached value, pending state, backup).
Fail fast
Return an error immediately rather than waiting.
Single point of failure
One component whose failure stops everything.
Service mesh
Infrastructure (sidecar proxies) that adds retries, security and metrics between services without code changes.
Bulkhead
Isolating resources per dependency so one can't exhaust all (part 2).
