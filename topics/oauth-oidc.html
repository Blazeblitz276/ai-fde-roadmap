Auth for apps and agents: OAuth 2.0 + OpenID Connect

Track: Production & ops + Cloud + Agentic. Builds on drop 1 (cloud IAM) and drop 2 (MCP).
Cloud IAM (drop 1) decides what your services may do inside your cloud account. OAuth 2.0 and OpenID Connect (OIDC) answer the same question for people, apps and agents talking to each other over the internet: who is this, and what are they allowed to touch, without anybody handing over a password.

What it is and the problem it solves

TermOne-line ideaProblem it solves
Authentication (AuthN)Proving who you areAnyone could claim to be anyone
Authorization (AuthZ)Deciding what you are allowed to doLogged-in users seeing or changing things they should not
OAuth 2.0 (2.1 is the tidied-up version)A standard way for a user to let an app act for them with a limited, expiring, revocable access tokenThe old habit of giving your password to third-party apps
OpenID Connect (OIDC)A thin identity layer on top of OAuth: adds an ID token that says who the user isOAuth alone says 'this token may read photos', not 'this is Asha'. 'Sign in with Google / Microsoft' is OIDC
Identity provider (IdP)The service that logs users in and issues tokens: Microsoft Entra ID, Amazon Cognito, Google Identity Platform, Okta/Auth0Every app building its own fragile login system

Why it matters more with agents: an AI agent calling Gmail, Jira or an MCP server on a user's behalf must carry a token that proves which user it acts for and limits what it may do. Get this wrong and an agent can read every mailbox in the company.

How it works: the authorization code flow with PKCE (the default)

  1. Redirect to the IdPThe app never sees the password. It sends the browser to the IdP saying who it is (client id), what it wants (scopes like calendar.read), and a PKCE challenge: a hash of a secret it keeps.
  2. User logs in and consentsThe IdP handles password, MFA, conditional access, and shows a consent screen: App X wants to read your calendar.
  3. Code comes back, gets exchangedThe IdP returns a short-lived code. The app swaps code + the PKCE secret for tokens over a back channel. PKCE means a stolen code is useless without the secret.
  4. Call the API with the access tokenEvery request carries an Authorization: Bearer header with the token. The API checks it was signed by the trusted IdP, has not expired, is meant for this API (audience), and has the needed scope.
  5. Refresh quietlyAccess tokens live minutes to an hour. A refresh token gets a new one without bothering the user; revoking it cuts the app off.

Everyday comparison: a hotel keycard.
Reception (the identity provider) checks your passport once (login). You get a registration slip saying who you are (ID token, OIDC) and a keycard (access token) that opens only your room and the gym (scopes), stops working at checkout (expiry), and can be cancelled at the desk (revocation). The room door (the API) never sees your passport; it only checks the card. A valet you lend a limited card to is the agent acting on your behalf.

Trade-offs: a managed IdP costs per active user but gives MFA, breach protection and audit logs you would never build well yourself. Short token lifetimes are safer but mean more refresh traffic. Do not use OAuth to replace your own authorization rules: a token saying role=manager still needs your code to check manager of which team. Do not roll your own login or JWT signing.

Pattern card: delegated, least-privilege tokens

What it is
Every caller (user, app, agent) presents a short-lived token from a trusted identity provider, scoped to only what it needs, and every API validates it on every call.
Metaphor
The hotel keycard: limited rooms, expires, revocable, the door never sees your passport.
Real example
The MCP specification (2026-07-28) makes protected MCP servers OAuth 2.1 resource servers; Microsoft Entra Agent ID gives agents their own identities with an on-behalf-of flow.
Use when
Any app with users, any API exposed beyond one service, any agent or MCP tool touching user data.
Do not use when
A local script on your own machine with no network exposure; or service to service inside one cloud, where managed identities/IAM roles are simpler.
Trade-offs
More moving parts (IdP config, redirect URLs, token validation) in exchange for no shared passwords, central MFA and one place to revoke access.
Instruction to AI / a teammate
Add Entra ID sign-in to the Next.js app using the authorization code flow with PKCE, protect the Python API by validating the JWT issuer, audience, expiry and the tickets.read scope on every route, and have the agent call the ticket API on behalf of the signed-in user, never with an admin key.

Real-world scenario and why it matters on the job

Model Context Protocol (MCP), specification version 2026-07-28: a protected MCP server acts as an OAuth 2.1 resource server and an MCP client (the agent app) as an OAuth 2.1 client. Servers must publish Protected Resource Metadata (RFC 9728) so clients can discover which authorization server to use; when a request has no valid token the server answers 401 with a pointer to that metadata. Clients must send the token in the Authorization header on every request, never in the URL, and servers must check the token was issued for them (audience binding, RFC 8707), so a token for one tool cannot be replayed against another. PKCE is mandatory: clients must refuse to proceed if the authorization server does not advertise it.

Microsoft Entra Agent ID: Microsoft documents agent identities in Entra, with an on-behalf-of flow where an interactive agent exchanges the signed-in user's token for a token to a downstream resource such as Microsoft Graph, so the agent acts as that user with that user's permissions rather than as an all-powerful app.

Why it matters: in FDE work the first security review question is whose permissions the agent uses. Being able to draw this flow, name the right IdP on the customer's cloud, and insist on per-user, scoped, audience-bound tokens is what gets an agent pilot through security sign-off (drop 6 scoping and guardrails).

Where it shows up in code you'll read

# Python (FastAPI-style), conceptually: the API checks every token
def current_user(token = header('Authorization')):
    claims = verify_jwt(token, issuer=IDP_URL, audience='api://tickets')  # signature, expiry, audience
    if 'tickets.read' not in claims['scp']:
        raise Forbidden()
    return claims['sub']          # the user's stable id

@app.get('/tickets')
def list_tickets(user = depends(current_user)):
    return db.tickets_for(user)   # your own authorization rule still applies
// Java / Spring Boot: look for Spring Security config, e.g.
//   http.oauth2ResourceServer(oauth2 -> oauth2.jwt(...))
//   @PreAuthorize('hasAuthority(SCOPE_tickets.read)') on a controller method
// TypeScript / Next.js: look for an auth library (Auth.js / NextAuth, MSAL, Amplify)
//   configured with an Entra ID / Cognito / Google provider, and middleware.ts
//   that redirects anyone without a session to /login.
// The point: login lives in the IdP, token checks live in middleware/config, not scattered in every function.

FDE / architect interview angle

  • An agent needs to read a user's emails and file tickets in Jira. How do you handle auth? Strong answer: the user signs in with OIDC (auth code + PKCE); the agent uses delegated, on-behalf-of tokens with the minimum scopes, never a shared admin key; tokens are short-lived and audience-bound; risky actions need human approval; everything is logged with the user id; access can be revoked centrally.
  • What is the difference between OAuth and OIDC? Strong answer: OAuth is authorization (an access token for an API); OIDC adds authentication (an ID token saying who the user is). Use OIDC to log in, OAuth access tokens to call APIs, and never treat an access token as proof of identity in your own app.

Glossary

AuthN / AuthZ
Authentication (who you are) / authorization (what you may do).
OAuth 2.0 / 2.1
Standard for delegated access via tokens; 2.1 consolidates best practices (PKCE required, unsafe flows removed).
OIDC
OpenID Connect: identity layer on OAuth that adds the ID token and standard user info.
IdP / authorization server
Service that logs users in and issues tokens (Entra ID, Cognito, Google Identity Platform, Okta).
Client
The app or agent asking for access.
Resource server
The API holding the data, which checks tokens.
Access token
Short-lived credential sent to an API; says what the caller may do.
ID token
OIDC token saying who the user is; for your app, not for calling APIs.
Refresh token
Longer-lived credential used to get new access tokens without a new login.
JWT
JSON Web Token: a signed, readable token format with claims like issuer, audience, expiry.
Claim
A field inside a token, e.g. sub (user id), aud (audience), exp (expiry), scp (scopes).
Scope
A named permission, e.g. calendar.read.
Audience
Which API a token is meant for; an API must reject tokens meant for others.
PKCE
Proof Key for Code Exchange: a one-time secret that makes a stolen authorization code useless.
Redirect URI
The pre-registered URL the IdP sends the user back to.
Consent
The screen where the user approves what the app may access.
Client credentials
Flow where a service authenticates as itself, no user.
On-behalf-of (OBO) / token exchange
Swapping a user's token for a narrower token to a downstream API, still as that user.
Managed identity / IAM role
Cloud-provided identity for a service, with no secret stored in code.
MFA / conditional access
Second factor at login / rules like only from company devices.
Protected Resource Metadata (RFC 9728)
A document an API publishes saying which authorization servers it trusts.
Bearer token
Whoever holds it can use it, so it must be short-lived and sent only in HTTPS headers.
