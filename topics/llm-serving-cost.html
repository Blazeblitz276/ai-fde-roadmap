LLM serving cost and latency: tokens, streaming, batching, model routing, provisioned throughput

What it is and the problem it solves

An LLM reads your prompt (input tokens) and then writes the answer one token at a time (output tokens). You pay per token (or per reserved capacity), and the user waits for two things: time to first token (how long until anything appears, mostly driven by prompt length and queueing) and time per output token (how fast the rest streams). Long prompts, long answers, a model bigger than needed, and traffic spikes are what make apps slow and expensive.

KnobSavesHow
Fewer tokensCost + latencyTrim system prompts and RAG context (top 5 chunks, not 20), cap output length, ask for concise formats
StreamingPerceived latencyShow tokens as they are generated (server-sent events) so the user reads while the model writes
CachingCost + latencyProvider prompt caching for repeated prefixes; semantic cache for repeat questions (drop 2)
BatchingCost (GPU efficiency)Self-hosted: continuous batching on the GPU (vLLM). Offline jobs: provider Batch APIs, typically discounted with results within ~24 h
Model routingCostSend easy requests to a small cheap model, hard ones to a big model
Provisioned throughputPredictable latency at steady volumeReserve dedicated capacity (Azure PTUs, Bedrock Provisioned Throughput, Google Provisioned Throughput) instead of shared pay-as-you-go

How it works

  1. Prefill (reading the prompt)The model processes all input tokens at once; long prompts raise time to first token. Prompt caching lets the provider reuse this work for an identical prefix.
  2. Decode (writing the answer)One token at a time; each step reuses a memory of earlier tokens (the KV cache). Output tokens are usually priced several times higher than input tokens.
  3. Batching on the GPUA GPU serving one request at a time sits mostly idle. Continuous batching lets many requests share each decode step; PagedAttention (vLLM) stores the KV cache in small blocks so far more requests fit in GPU memory.
  4. Capacity modelPay-as-you-go shares capacity and can throttle (HTTP 429) at peaks; provisioned throughput reserves capacity billed per hour whether used or not, so it pays off only at steady, high utilisation.
Everyday comparison: a restaurant kitchen
Input tokens are reading the order, output tokens are cooking each dish. Streaming is serving starters while mains cook. Batching is cooking twelve dosas on one big tawa instead of one at a time. Routing is the junior cook making tea while the head chef does the biryani. Provisioned throughput is booking the whole restaurant for your event: guaranteed tables, but you pay even if guests don't show.

Real-world scenarios (verified)

LMSYS / Chatbot Arena on vLLM
The vLLM team (UC Berkeley) reported in June 2023 that LMSYS's FastChat used vLLM as the backend for Vicuna and Chatbot Arena, cutting the number of GPUs used to serve that traffic by 50%, while handling an average of 30K requests a day and a peak of 60K. vLLM's PagedAttention delivered up to 24x higher throughput than Hugging Face Transformers in their tests.
RouteLLM (LMSYS research)
LMSYS's open-source RouteLLM (July 2024) routes each prompt between a strong and a weak model; on the MT Bench benchmark it reported cost reductions of over 85% while keeping 95% of GPT-4's performance (smaller savings on other benchmarks). A research result, not a guarantee: calibrate on your own traffic.
Azure PTUs
Microsoft Foundry's provisioned throughput: you buy PTUs (model-independent capacity units) billed per hour; throughput per PTU varies by model and each model has a minimum size, so you size from your tokens-per-minute estimate.
Why it matters on the job
Customers judge pilots on 'it feels fast' and the first invoice. Being able to say 'time to first token is 2.8 s because the prompt is 12k tokens; caching the prefix and routing FAQs to a mini model brings it to under 1 s and cuts cost by about half' is exactly the architect conversation.

Pattern card: model router + capacity tiers

What it is
A gateway that picks the cheapest model that can handle each request and the right capacity pool (provisioned first, pay-as-you-go overflow).
Metaphor
Hospital triage: a nurse handles minor cases, specialists get the complex ones, and the reserved operating theatre is used before booking extra rooms.
Real example
RouteLLM (LMSYS); Azure API Management's AI gateway features in front of Azure OpenAI deployments.
Use when
Mixed difficulty traffic at meaningful volume, or throttling at peak.
Do not use when
Low volume (savings smaller than the engineering), or every request truly needs the top model.
Trade-offs
Lower cost and smoother latency vs router mistakes, more moving parts, and per-route evals to maintain.
Instruction to AI / a teammate
Put an AI gateway in front of our models: stream all chat responses, cap output at 500 tokens, route FAQ-type requests to the mini model, send the rest to the large model's provisioned deployment with pay-as-you-go spillover on 429, and log tokens, cost and time-to-first-token per request.

FDE / architect interview angle

  • Our assistant costs $40k a month and feels slow. What do you do first? Strong answer: measure (tokens in/out per request, time to first token, cache hit rate, which routes cost most), then trim context, cache prefixes, stream, route easy traffic to a small model, batch offline jobs, and only then consider provisioned capacity, all checked against an eval set so quality holds.
  • When would you buy provisioned throughput? Strong answer: steady, predictable high volume with latency SLOs where PAYG throttles; size to the baseline from real TPM data, spill peaks to PAYG, and compare the hourly cost against current token spend.

Glossary

Token
A chunk of text (roughly 3/4 of an English word) that models read, write and bill by.
Input / output tokens
Tokens you send (prompt + context) / tokens the model generates.
Time to first token (TTFT)
Delay before the first word of the answer appears.
Prefill / decode
The model's two phases: reading the whole prompt / generating one token at a time.
KV cache
The model's working memory of earlier tokens, stored on the GPU during generation.
Streaming / SSE
Sending the answer piece by piece as it is generated; server-sent events is the usual web mechanism.
Continuous batching
Letting many requests share each GPU step, adding new ones as others finish.
PagedAttention
vLLM's technique of storing the KV cache in small blocks, like memory pages, to fit more requests.
vLLM
A popular open-source engine for serving LLMs on your own GPUs.
Batch API
A provider endpoint that runs many requests offline at a discount with slower turnaround.
Model routing / AI gateway
Choosing a model per request / the proxy layer that does routing, quotas and logging.
PAYG
Pay-as-you-go: pay per token on shared capacity.
Provisioned throughput / PTU
Reserved model capacity billed per hour; PTU is Azure's unit for it.
TPM
Tokens per minute, the usual way to size capacity and quotas.
429
The HTTP 'too many requests' error you get when throttled.
MT Bench
A public benchmark of multi-turn chat questions used to compare models.
